# Data pipeline

How Paletter's data is captured from Bedrock Dedicated Server (BDS), turned into the component model and generated
code, and kept up to date. Everything here runs from the `tools` module, which is never published.

```
BDS (downloaded and run)   -> update, capture, spec-capture, behaviour-probe, ... -> data/bds/<build>/
data/bds + Geyser files    -> import / update                    -> paletter/src/main/resources/paletter/*.nbt
creator docs               -> docs                               -> data/model/components.json
data/model + spec capture  -> infer                              -> data/model/mappings.json, coverage.md
data/model                 -> generateComponentApi               -> paletter/src/generated/java (components, encoders, behaviour keys)
bundled data               -> generateConstants                  -> paletter/src/generated/java (vanilla constants)
data/bds + third party     -> behaviour import                   -> behaviour.nbt, data/behaviour/REPORT.md
data/bds/<build>/voxel-shapes -> voxel-shapes import             -> voxel_shapes.nbt
```

Downloading BDS means accepting the [Minecraft EULA](https://minecraft.net/eula).

## Layout and markers

- `data/bds/<build>/`: what one BDS build gave, captured by a tool in this repository and never edited by hand. A
  capture is replaced by running its command again. Each `capture.json` records the `platform` of the BDS it ran
  (`windows`; the tools run the Windows build on Windows and the Linux build elsewhere). Windows and Linux BDS number
  custom blocks, order the creative inventory and encode some component NBT differently, so captures of different
  platforms are never compared: `update` refuses to run on another platform than the committed captures', and the
  conformance suites fail if `data/bds` mixes platforms.
- `data/model/`: the component model. `components.json`, `mappings.json`, `coverage.md`, `bds-feedback.json`,
  `bds-keys.json` and `constants-history.json` are generated; `fixtures.json` and `api.json` are written by hand.
  [ATTRIBUTION.md](../data/model/ATTRIBUTION.md) covers the creator documentation they derive from.
- `data/addons/`: the packs run on BDS. `capture` and `creative` are generated by `addon`; `dump`, `behaviour-dump` and
  `probe` are written by hand.
- `data/behaviour/REPORT.md`: generated by `behaviour import`.

Every generated file says so and names the command that writes it: a `// Generated by` header in Java and text files,
a first key `_generated` in JSON, a root string `_generated` in bundled `.nbt` files, the manifest description in packs.
Hand-written inputs carry no marker. `GeneratedMarkersTest` checks this.

## Commands

All tools share one command line: `./gradlew :tools:run --args="<command> ..."`. `--help` lists the commands, and each
command takes `--help`. Paths are relative to the repository root (`--root` overrides).

| Command | Does |
|---|---|
| `update` | The whole BDS pipeline (below). |
| `capture`, `compare`, `experiments` | The headless client: record what a server sends, diff a capture with a bundled version, toggle experiments in a `level.dat`. |
| `import`, `bds-compare`, `verify`, `check-data` | Import and check bundled data. `check-data` lists what older versions lack. |
| `data-diff`, `experiment-marks` | Maintain bundled data without a new capture. |
| `bds-inventory` | Reads the strings of the Linux `bedrock_server` without running it: block and item components, Script API classes. |
| `docs`, `addon`, `spec-capture`, `infer`, `check-mappings` | The component model (below). |
| `components generate\|check`, `constants generate\|check` | The generators (below). |
| `behaviour import`, `behaviour-probe`, `behaviour-dump` | Behaviour values (below). |
| `voxel-shapes capture\|import\|check` | Voxel shape captures and `voxel_shapes.nbt`. |
| `creative-probe` | Runs an add-on on BDS and records the creative inventory order. |
| `education-capture` | Records what only an Education Edition world adds (`education.json`, used for `@Education`). |
| `inspect` | Prints `Palette#explain` for a block state or item in one or all bundled versions. |

Gradle tasks: `generateConstants`, `generateComponentApi`, `generateComponentApiPreview`, `generateModel`,
`generateAddon` and `inferMappings` write; `checkConstants`, `checkComponentApi` and `checkMappings` (strict) are part
of `./gradlew build` and fail when committed output is stale, `checkData` fails on problems of the bundled data.

Generator tests compare against golden files. After an intended change of generator output, run
`./gradlew :tools:test -PupdateGolden=true` and review the diff.

## Updating for a new BDS build

```
./gradlew :tools:run --args="update --channel release"                  # update the repository
./gradlew :tools:run --args="update --channel release --verify-only"    # write nothing, exit 1 on any difference
```

Useful options: `--version <build>` for a specific build, `--channel preview` for the newest preview,
`--keep-server`, `--cache DIR` (default `$PALETTER_BDS_CACHE`, else the Gradle user home), `--report FILE`, and
`--experiments a,b` to skip experiment discovery. Run `update --help` for the rest.

A run downloads BDS and, in `<cache>/runs/<platform>-<version>/`:

1. Runs the Script API dump pack (`data/addons/dump`).
2. Captures a vanilla world with the headless client: item registry, creative inventory and block properties. Every
   creative block id is checked against the computed state hash. It captures again with sequential ids.
3. Discovers the build's experiment toggles (below) and captures with each one.
4. Captures the add-on world (`data/addons/capture`) and keeps its content log.
5. Checks the assumptions the library relies on: sequential block ids sorted by name hash, custom block ids from 10000
   in descending identifier order, custom block items at `255 - block_id`, and the creative order rule.
6. Compares everything against the committed data: a build with committed captures against its own, a build not
   bundled yet against the newest older build. Only the latter can show new protocol windows: a changed wire shape
   needs a review of the component model.
7. Unless `--verify-only`: imports a new protocol as a new bundled version, or refreshes item tags and default states of
   an existing one; writes the new captures; regenerates the component API and the vanilla constants.

The report starts with a one-line verdict and lists only what failed, changed or needs a decision ("Needs attention",
each with what to do), then what the build changed; every check, the run's metadata and the evidence are collapsed
below. An update writes it to
`data/bds/<build>/update-report.md` (generated, committed with the data, so a later run can be diffed against it; a run
that changed no data file leaves the committed report and writes its own only into its work directory) and
exits with 2 while decisions are open. As `./gradlew :tools:run` turns every non-zero exit into exit code 1, a run also
writes its exit code to `exit-code` in its work directory. Things that stay manual:

- reviewing wire format changes in `data/model` and the regenerated component API;
- re-importing a protocol whose network data changed in a hotfix;
- the order of states inside newly generated blocks, which BDS does not expose (`Update#keyOrder` infers it from the
  previous release; check against CloudburstMC/Data with `verify` once it has the version);
- adding a codec for a new protocol to the Cloudburst protocol library.

The capture client uses RakNet when the server answers a RakNet ping and NetherNet otherwise (1.26.70 previews only
speak NetherNet). With `online-mode=false` no Xbox sign-in is involved.

### Experiments

Bedrock has no list of its experiment toggles, so `update` discovers them (`ExperimentDiscovery`). Candidates are
identifier-like strings from the server binary plus known ids. All candidates are written into a fresh world's
`level.dat`; BDS keeps only the keys it knows and logs one code per toggle. Toggles that start game still streams are
current, the others retired. Each current toggle is then captured on its own to attribute content to it.

The result is committed as `data/bds/<build>/experiments.json`, and the bundled version gets experiment marks: per
toggle, the items, blocks and creative stacks it adds. The bundle itself is captured without experiments.

### Previews

Paletter bundles the newest preview next to the releases. `update --channel preview` imports it like a release, marked
`preview` in `versions.txt`; the library serves it only when `paletter.previews` is `true`. Generated API that only the
preview has (constants, states, enum values, components and fields BDS releases reject) is marked
`@SincePreview("<version>")` and is kept out of `constants-history.json`. Importing a newer preview, or the preview's
release, drops the bundled preview and its `data/bds/<build>` captures. Release runs never compare against a preview's
captures.

### Other sources

`verify --source DIR --name 26.60` diffs a directory in the CloudburstMC/Data layout (Geyser's file names work too)
against a bundled version: block states and order, hashes, items, components, data driven blocks and the creative
layout. It writes only a report.

Vanilla block palette order cannot be observed from the Script API or the network, which is why bundled palettes still
descend from CloudburstMC/Data and Geyser files and are verified against BDS rather than generated from it. The
bedrock-samples metadata and the BDS `definitions/` folder are not used: they miss items, lack defaults or order, or
hold nothing Paletter needs.

### CI

- `build.yml` runs `./gradlew build` on pushes to `main` and on pull requests. Its `check` includes `:tools:checkMappings`
  (`check-mappings --strict`: every captured bit and wire path is explained) and `:tools:checkData` (`check-data`).
- `bds-data.yml` runs `update` once a day for the release and preview channels on Windows BDS (a Windows runner, like
  the committed captures), then `generateComponentApi` and `:paletter:apiDump`. On a failure or a difference it opens
  or comments on an issue and opens a pull request from `bds-data/<channel>` with the updated data (only data and
  generated paths; the issue and pull request bodies are written to the runner's temp directory). A clean run (no
  failure, no difference, no data file changed) closes the channel's open issue that the workflow opened; a manual run
  of an explicit version closes nothing. A manual run can pick one channel and stop after the report (`verify-only`).
  The capture job runs BDS and Gradle with a read-only token and no secrets; a separate publish job, which runs no
  build, applies the data patch (rejected if it touches other paths) and writes the issue and pull request. A patch
  that changes generated code needs the `BDS_DATA_TOKEN` secret, so the build runs on its pull request.
- `javadoc.yml` publishes the Javadoc of `main` and of each release to GitHub Pages.
- [releasing.md](releasing.md) lists the repository settings, secrets and Pages setup these workflows need.

## The component model

The custom item and block API mirrors Bedrock's add-on components. Its model is built only from the official creator
docs and from what BDS does.

```
./gradlew :tools:generateModel [-Pdocs=<minecraft-creator checkout>]  # docs -> components.json
./gradlew :tools:generateAddon                                         # spec add-on -> tools/build/spec-addon
./gradlew :tools:run --args="spec-capture --channel release"           # run it on BDS -> data/bds/<build>/spec
./gradlew :tools:inferMappings                                         # -> mappings.json, coverage.md, bds-feedback.json
```

**Docs.** `DocsParser` reads the component pages of MicrosoftDocs/minecraft-creator at a pinned commit into
`components.json`: per component its fields, types, defaults, enums, ranges, format versions and experiments.

**Variants.** The spec add-on has, per component, a control, a base with every required field set, and one variant per
field value. Values come from the field's type: limits and one past each, enum values plus an invalid one, empty and
wrong-length lists, and so on. Limits come from the docs and from `bds-feedback.json`, which records what BDS's content
log said last time; `spec-capture` and `infer` are repeated until that file stops changing. When BDS rejects a variant
for a member it does not vary, `spec-capture` shrinks the variant and captures again.

**What BDS says that the docs do not.** BDS wins over the docs. Type errors in the content log become errata.
`spec-capture --probe-keys` asks BDS about keys the docs leave out, using candidates from the BDS binary, the bedrock
wiki and vanilla packs (only as names, never as values); accepted keys land in `data/model/bds-keys.json`.
`spec-capture --format-sweep` captures components at the `format_version` boundaries, as evidence for hand transforms.

**Inference.** A variant is accepted when BDS sent it and logged no error. For each field, every wire leaf that changed
against the base is explained by the first rule that fits all observations: `identity`, `linear`, `table`, `affix`,
`bitset`, `ordered-set`, `element`, or a constant switched on by the field's presence. `whenAbsent` records what BDS
sends when the field is omitted. Fields no rule explains need a hand transform. Captures from different builds that
differ become separate protocol windows in `mappings.json`.

The inference fails `check-mappings --strict` and `update` on integer bits no field explains and on wire paths that
are neither mapped nor classified. [data/model/coverage.md](../data/model/coverage.md) lists the result per component,
including fields that need a hand rule and hand transforms BDS has not verified.

`ComponentConformanceTest` rebuilds every variant BDS accepted through the generated API and compares Paletter's NBT
with BDS's, for every captured build. It has no list of exceptions: a variant the API cannot express, or encodes
differently, fails the build. Such gaps are closed in the model (`api.json` `optional`, `openEnums`, `unions`, `forms`,
protocol windows) or with a hand transform, never waived.

## Code generation

### Component API

`./gradlew :tools:generateComponentApi` writes the component records in `item.component` and `block.component`, the
sealed `ItemComponent`, `BlockComponent` and `BlockTrait`, and the encoders in `internal.component` (`ItemWire`,
`BlockWire`, `TraitWire`, `ComponentIndex`, `TraitStateTable`). The generator lives in its own `componentApi` source set,
so it runs even when `paletter` does not compile.

Inputs, all in `data/model` except the last:

- `components.json`: components, fields, defaults, docs text.
- `fixtures.json` (hand): errata, samples, `replacedBy` with evidence.
- `bds-feedback.json`: required fields and ranges BDS enforces, which win over the docs.
- `mappings.json`: per component and protocol window, how each field reaches the wire.
- `api.json` (hand): Java shape only (names, unions, value forms, open enums).
- `HandTransforms` (hand, in the tools): which fields are compiled by a method of `internal.component.Transforms`.
  Each method's Javadoc says why no inferred rule fits and what evidence backs it.

Rules the generator follows:

- Defaults are the documented ones, unless BDS sends something else for an omitted field; then the field stays unset
  and the encoder writes BDS's value.
- Required fields, ranges and step sizes are checked in `build()`.
- A field with no rule in a protocol window is dropped there with a report warning.
- `@ServerOnly`, `@Deprecated` and `@ReplacedBy` come from the data: the windows' status, the docs status, BDS's
  rejection message, or a `fixtures.json` `replacedBy` entry.
- Every component in the docs is generated, including ones BDS never sends. Components that cannot be generated are
  listed with the reason in the Javadoc of the sealed interfaces.
- Generation fails on two mappings for one protocol, name collisions, two fields writing one wire leaf, or an
  ambiguous union.

### Behaviour keys

The same task writes `BlockBehaviour`, `ItemBehaviour` and `internal.behaviour.WireRules`, which reads a key from the
component data of a custom block or item. The hand-kept table `BehaviourKeys` in the tools names each key's type, Javadoc,
BDS sources and, for keys custom content sets, its component field. The field's rule in `mappings.json` is read
backwards; where the behaviour probe measured engine values against component values (friction), the fitted relation
converts them. Shapes use the hand-written `internal.behaviour.ShapeRules`.

### Vanilla constants

`./gradlew :tools:generateConstants` writes `BedrockBlocks`, `BedrockStates`, `BedrockItems`, the enums in
`vanilla.state`, with what only a bundled preview has marked `@SincePreview`. Inputs: the newest bundled release and
preview, `renames.txt` and `data/model/constants-history.json`, which records every constant ever generated so
regeneration cannot drop one. Commit the history together with the classes.

- Names are the UPPER_SNAKE of the identifier path. Collisions fail until a name override in `ConstantsGenerator`
  settles them.
- A state keeps its type and enum; a state that changes kind fails generation.
- Removed content stays as a deprecated constant: an alias where the identifier moved, otherwise resolving to
  `minecraft:unknown`.
- `@since` is the first bundled release that has the content without an experiment, from
  `data/bds/<build>/experiments.json`.
- `internal.vanilla.BlockLayout` checks that each block's states are the full cartesian product of its values, so state
  ids can be computed from strides.

## Behaviour data

```
./gradlew :tools:run --args="behaviour import --cloudburst-data <checkout> --allay <checkout>"
```

writes `behaviour.nbt` and `data/behaviour/REPORT.md` from:

- Paletter's own captures under `data/bds`: Script API dumps (`behaviour-dump`, run with the Beta APIs), and
  experiments on BDS (`behaviour-probe`: door collision, climbing, and the defaults of custom blocks);
- CloudburstMC/Data (Apache-2.0) and AllayMC/Allay (MIT), read from their git history and matched to versions by block
  state hashes. These are third-party and labelled as such.

The report lists the ranking, which source decides each key in each version, disputes and post-processed values. The
same sources at the same commits give the same bytes. Keys that only have third-party sources are the `NATIVE:` ones in
the report; [native-capture.md](native-capture.md) is the plan for capturing them from BDS.

## Voxel shapes

`voxel-shapes capture --version <build>` (also part of `update`) records the voxel shapes packet of a vanilla world,
of a world with the `voxel_shapes` experiment, of a probe add-on and of anchor blocks, plus BDS's own shape files, into
`data/bds/<build>/voxel-shapes`. `voxel-shapes import` writes `voxel_shapes.nbt`; `VoxelShapeConformanceTest` checks the
library against every capture. The findings are in [wire-notes.md](wire-notes.md#voxel-shapes).
