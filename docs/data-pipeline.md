# Data pipeline

How Paletter's data is captured from Bedrock Dedicated Server (BDS), turned into the component model and generated
code, and kept up to date. Everything here runs from the `tools` module, which is never published.

```
BDS (downloaded and run)   -> update, capture, spec-capture, behaviour-probe, ... -> data/bds/<build>/
data/bds + Geyser files    -> import / update                    -> paletter/src/main/resources/paletter/*.nbt
creator docs               -> docs                               -> data/model/components.json
BDS docgen (`update`)      -> bds-schema                         -> data/bds/<build>/schema.json (merged into the model by `Fixtures#apply`)
data/model + spec capture  -> infer                              -> data/model/mappings.json, coverage.md
data/model                 -> generateComponentApi               -> paletter/src/generated/java (components, encoders, behaviour keys)
bundled data               -> generateConstants                  -> paletter/src/generated/java (vanilla constants)
BDS binary (not run)       -> whitebox, whitebox-coverage         -> data/bds/<build>/whitebox.json, whitebox-coverage.md
data/bds + third party     -> behaviour import                   -> data/behaviour/captures.nbt, REPORT.md, generated behaviour data
data/behaviour/captures.nbt -> generateBehaviour                 -> paletter/src/generated/java (internal.behaviour.vanilla)
bundled palettes           -> generateBlocks (import / update)   -> paletter/src/generated/java (internal.vanilla.blocks); the
                                                                    version files lose their block states
data/bds/<build>/voxel-shapes -> voxel-shapes import             -> paletter/src/generated/java (internal.vanilla.shapes)
```

Maintainers: [updating.md](updating.md) is the short runbook for the recurring jobs.

Downloading BDS means accepting the [Minecraft EULA](https://minecraft.net/eula).

## Layout and markers

- `data/bds/<build>/`: what one BDS build gave, captured by a tool in this repository and never edited by hand. A
  capture is replaced by running its command again. Each `capture.json` records the `platform` of the BDS it ran
  (`windows`; the tools run the Windows build on Windows and the Linux build elsewhere). Windows and Linux BDS number
  custom blocks, order the creative inventory and encode some component NBT differently, so captures of different
  platforms are never compared: `update` refuses to run on another platform than the committed captures', and the
  conformance suites fail if `data/bds` mixes platforms. `data/bds/builds.json` (generated by
  `builds check`) lists every release build checked and whether its captures are kept.
- `data/model/`: the component model. `components.json`, `mappings.json`, `mappings-evidence.json`, `coverage.md`, `bds-feedback.json`,
  `bds-keys.json`, `variant_names.txt`, `baseline-26.20.txt`, `constants-history.json`, `api-history.json` and
  `vanilla-shapes-known-<protocol>.txt` (the vanilla shape disagreements `VanillaShapeOracleTest` knows, written with
  `-PupdateShapeDisagreements=true`) are generated; `fixtures.json`, `api.json` and `constant-names.txt` are written by hand.
  [ATTRIBUTION.md](../data/model/ATTRIBUTION.md) covers the creator documentation they derive from.
- `data/addons/`: the packs run on BDS. `creative` is generated by `addon`; `dump`, `behaviour-dump` and
  `probe` are written by hand.
- `data/behaviour/REPORT.md`: generated by `behaviour import`.

Every generated file says so and names the command that writes it: a `// Generated by` header in Java and text files,
a first key `_generated` in JSON, a root string `_generated` in bundled `.nbt` files, the manifest description in packs.
Hand-written inputs carry no marker. `GeneratedMarkersTest` checks this.

## Commands

All tools share one command line: `./gradlew :tools:run --args="<command> ..."`. `--help` lists the commands, and each
command takes `--help`. Paths are relative to the repository root (`--root` overrides).

| Command | Does |
|---|---|
| `update` | The whole BDS pipeline (below). |
| `builds list\|check\|table\|resolve\|record\|plan` | Every release build, one by one, against the previous kept build ([below](#every-release-build)): `table` writes what `builds.json` says per data version, `resolve` names the newest build of a channel, `record` brings `builds.json` up to date without BDS, `plan` lists the builds of a [full recapture](#full-recapture). |
| `capture`, `compare`, `experiments` | The headless client: record what a server sends, diff a capture with a bundled version, toggle experiments in a `level.dat`. |
| `import`, `bds-compare`, `verify`, `baseline`, `check-data` | Import and check bundled data. `check-data` lists what older versions lack. |
| `export` | Writes what a compiled palette of a data version sends in the file formats of CloudburstMC/Data, to compare with `verify --against` ([updating.md](updating.md), section a). |
| `bds-schema` | `data/bds/<build>/schema.json` from the `json_schemas` of BDS's documentation generator ([BDS schema](#bds-schema)). |
| `data-diff`, `experiment-marks` | Maintain bundled data without a new capture. |
| `bds-inventory` | Reads the strings of the Linux `bedrock_server` without running it: block and item components, Script API classes. |
| `whitebox`, `whitebox-coverage` | Reads the code of the server binary without running it: what each component can send, and what no capture shows of it ([below](#white-box-discovery)). |
| `docs`, `addon`, `spec-capture`, `infer`, `check-mappings` | The component model (below). |
| `retire <window protocol>` | Drops a protocol from `mappings.json` and `mappings-evidence.json` and lists what else of it must go ([updating.md](updating.md), section h). |
| `components generate\|check`, `constants generate\|check` | The generators (below). |
| `behaviour import`, `behaviour-probe`, `behaviour-dump` | Behaviour values (below). |
| `script-dump` | Runs the Script API dump add-on on one BDS build: `data/bds/<build>/dump.json.gz` and the item variant names (below). |
| `voxel-shapes capture\|import\|check` | Voxel shape captures and the generated shape classes ([Voxel shapes](#voxel-shapes)). |
| `blocks generate\|check` | The vanilla block definitions as generated code ([Block definitions](#block-definitions)). |
| `creative-probe` | Runs an add-on on BDS and records the creative inventory order. |
| `education-capture` | Records what only an Education Edition world adds (`education.json`, used for `@Education`). |
| `recipes-capture` | Records the crafting and trim data of one build (`vanilla/crafting_data.json.gz`, `vanilla/trim_data.json`); `update` writes them too. |
| `recipes-diff` | `--from <build> --to <build>`: diffs two committed recipe captures ([Recipes](#recipes)); exits with 1 on a difference. |
| `recipes-import [--check]` | The recipe captures of `data/bds` to the bundled recipes of `paletter-recipes` ([Recipes](#recipes)); `:tools:checkRecipes` (part of `check`) runs `--check`. |
| `inspect` | Prints `Palette#explain` for a block state or item in one or all bundled versions. |

Gradle tasks (each with the command it runs: [updating.md](updating.md)): `generateConstants`, `generateComponentApi`, `generateComponentApiPreview`, `generateModel`,
`generateAddon`, `generateBlocks` and `inferMappings` write; `checkConstants`, `checkComponentApi`, `checkBlocks`, `checkVoxelShapes`,
`checkMappings` (strict) and `checkWhitebox` are part of `./gradlew build` and fail when committed output is stale, `checkData` fails on
problems of the bundled data.

The generator tests assert on fragments of what they generate from small synthetic fixtures and compile the output (the component
and the constants generators), and the committed output is held up to date by `checkConstants` and `checkComponentApi`, so a change
of real output shows as a diff of the generated sources. Only two small golden files remain, for the synthetic variants and the API
dump of a fixture (`./gradlew :tools:test -PupdateGolden=true` rewrites them; review the diff).

## Updating for a new BDS build

```
./gradlew :tools:run --args="update --channel release"                  # update the repository
./gradlew :tools:run --args="update --channel release --verify-only"    # write nothing, exit 1 on any difference
```

Useful options: `--version <build>` for a specific build, `--channel preview` for the newest preview,
`--keep-server`, `--cache DIR` (default `$PALETTER_BDS_CACHE`, else the Gradle user home), `--report FILE`, and
`--experiments a,b` to skip experiment discovery. Run `update --help` for the rest.

A run downloads BDS and, in `<cache>/runs/<platform>-<version>/`:

1. Runs the Script API dump pack (`data/addons/dump`). BDS's documentation generator runs first, for the potion effect
   list the pack's tipped arrow loot tables (`set_potion`, one per effect) are written from. The dump includes
   `item_variants`: the aux values BDS accepts of potions, tipped arrows, beds and banners, with the Script API's potion
   effect or the localization key of each. If that part fails, the add-on reports an error and leaves it out, the rest of
   the dump stands, and the names stay as they are. `update` turns the variants into `data/model/variant_names.txt` (only
   the variants the version's creative inventory has; a creative variant without a name fails). Each variant is one line,
   `<first>..<last> <item> <aux> <name>`, with the bundled data versions (in `versions.txt` order) it exists in, both
   included; a range that reaches the newest version has no `<last>` (`26.60.. minecraft:bed 14 BED_RED`), so a new version
   that keeps the variant changes no line. The versions are needed because the release and the preview each have their own
   names (preview-only ones become `@SincePreview`), which `constants-history.json` does not know. `generateConstants`
   turns into `BedrockItemVariants`. The names are BDS's own spellings, never renamed: a name in `constants-history.json`
   keeps its identifier and aux, and a different name BDS gives the same variant makes the old one a deprecated alias.
2. Captures a vanilla world with the headless client: item registry, creative inventory and block properties. Every
   creative block id is checked against the computed state hash. It captures again with sequential ids.
3. Discovers the build's experiment toggles (below) and captures with each one.
4. Captures the creative order probe world (`data/addons/creative`), hashed and with sequential block ids. Then the palette
   probe (`data/addons/palette-probe`): in a world with sequential block ids and the build's current toggles on, its script
   places every state of every block type into a barrier-walled cell of its own next to the spawned capture client, which
   records the block update BDS sends for each cell. The pairs are `vanilla/sequential-ids.json.gz` (`PaletteIds`): the id of
   every state, not only of the creative stacks, so the order of the states within each block is BDS's (`PaletteIdsTest`
   holds the committed files to the bundled palettes; the run reports them against its reference palette, INFO only).
5. Checks the assumptions the library relies on: sequential block ids sorted by name hash, custom block ids from 10000
   in descending identifier order, custom block items at `255 - block_id`, and the creative order rule.
6. Compares everything against the committed data: a build with committed captures against its own, a build not
   bundled yet against the newest older build. Only the latter can show new protocol windows: a changed wire shape
   needs a review of the component model.
7. Unless `--verify-only`: imports a new protocol as a new bundled version, or refreshes item tags and default states of
   an existing one; writes the new captures; regenerates the component API and the vanilla constants.

The report starts with a one-line verdict and lists only what failed, changed or needs a decision ("Needs attention",
each with what to do), then what the build changed; every check, the run's metadata and the evidence are collapsed
below. An update writes it to
`data/bds/<build>/update-report.md` (generated, committed with the data, so a later run can be diffed against it; a run
that changed no data file leaves the committed report and writes its own only into its work directory) and
exits with 2 while decisions are open. `./gradlew :tools:run` turns every non-zero exit into exit code 1; the launcher of
`./gradlew :tools:installDist` (`tools/build/install/tools/bin/tools`), which the workflows run, passes the code on. Things
that stay manual:

- reviewing wire format changes in `data/model` and the regenerated component API;
- re-importing a protocol whose network data changed in a hotfix;
- the order of states inside newly generated blocks, which BDS does not expose (`ReferencePalette#keyOrder` infers it from the
  previous release; check against CloudburstMC/Data with `verify` once it has the version);
- adding a codec for a new protocol to the Cloudburst protocol library;
- the version pins and the `BDS_DATA_TOKEN` rotation, all listed in [updating.md](updating.md#pins).

The capture client uses RakNet when the server answers a RakNet ping and NetherNet otherwise (1.26.70 previews only
speak NetherNet). With `online-mode=false` no Xbox sign-in is involved.

### Every release build

`update` captures one build. The release builds between those (hotfixes, several of which can share a protocol) are
checked one by one:

```
./gradlew :tools:run --args="builds list --from 1.26.30"            # the builds, and what data/bds/builds.json says of each
./gradlew :tools:run --args="builds check --from 1.26.30 --limit 1"  # check the next unchecked build
./gradlew :tools:run --args="builds resolve --channel preview"        # the newest build the download links API names
```

The download links API is parsed in one place, `BdsDistribution.downloadUrl`; the BDS data workflow asks `builds resolve`
for the build it checks, so an API change fails there with the answer quoted.

**Zip checksums and frozen builds.** `data/bds/builds.json` records, per kept build and platform (`win`, `linux`), the
sha256 and size of its zip from minecraft.net (`zips`), computed from a downloaded zip and `unknown` when none was at hand;
nothing is guessed. `BdsDistribution.zip` checks a download, and a cached zip, against it: a zip minecraft.net serves
differently under the same name fails instead of being captured. `builds check` records them for the builds it keeps;
`builds record` brings the record up to date with the committed data without BDS or the network (release builds with
captures it lacks, checksums from the cache). A kept build whose zip can no longer be downloaded is frozen with the reason
(`builds record --freeze <build>=<reason>`, `--unfreeze <build>`): its captures stay, and `builds plan` leaves it out of a
full recapture with a `SKIPPED` line in the plan's summary.

The list of builds comes from [Bedrock-OSS/BDS-Versions](https://github.com/Bedrock-OSS/BDS-Versions), since the
download links API only names the newest build; the zips still come from minecraft.net. Each run reads the list at the
newest commit that changed it and records that commit (`listCommit`, `listDate`) in `data/bds/builds.json`. The
current release of the download links API (Mojang's own, so authoritative for the newest build) joins the list when the
list lacks it and it is newer than every listed build; the run notes that, and warns when the two disagree otherwise.
Each recorded build says where its number came from (`source`: `BDS-Versions` or `links API`). Every build number of the list, and every
`--from`, `--to` and `--against`, must be a build number (a bound: one to four dotted numbers), since build numbers name
directories that are deleted; paths built from them are checked to stay in their directory as well.

**Build numbers.** `1.<minor>.<patch>.<revision>`: four dotted numbers of at most nine digits, the first `1`
(`1.26.63.1`; leading zeros stay, `1.21.73.01`). The data version of a build is its line, the minor and the patch rounded
down to tens (`1.26.63.1` is `26.60`), and a preview reports its revision as a beta (`1.26.70.24` reports
`1.26.70-beta24`). `BuildNumber` (tools) is the only code that parses, rounds or reports them; the workflows check them
with its regex (`BUILD_RE`, kept equal to `BuildNumber.REGEX` by `BuildNumberTest`). A new format from Mojang fails there.

`builds check` takes the builds of the range that the record lacks, oldest first, and runs `update --against <kept
build>` on Windows BDS for each: the previous kept build, or the next one when nothing older is kept (the first builds
of the record, which may then be identical to a newer build). That captures everything an update captures, but compares
it with the committed captures of that build instead of the newest ones, version stamps aside (`bdsVersion`,
`protocol`, `_generated` and the packs' `formatVersion`, at the top level of a capture and of the packet the voxel
shape anchors embed, nowhere else):

- the Script API dump (block states, items, item and block tags, block defaults), the BDS inventory and the Script API
  getters it lists, the experiment record and the experiment self-checks (discovery, current toggles, resource pack
  stack), the voxel shapes, the creative inventory of the creative order probe, and
  the spec capture, value by value and in what BDS accepts and logs per variant;
- the network data (block palette, items, components, creative layout) against the bundled data version whose window
  holds the build's protocol. That is the data of the newest committed build of that version, so two builds compare
  equal through it.

A build is identical only when every one of these checks is. Some checks can only be made against the bundled data
version: block numbering and block hashes (an older hotfix may have experimental states the bundled version lacks), the
experiment marks, item tags and block defaults, and the creative order on the bundled layout. They decide nothing, and
the report lists them under "Not compared" with what compares the same thing build to build (mostly the Script API
dump). So does a capture the other build lacks (an older `update` run made no creative order probe inventory, say). The record keeps that list with the build (`notCompared`), since the report of an identical
build is not kept. The report notes when the two builds speak different protocols. The spec captures are only compared
when both were made with the same spec add-on (the same variants, with the same JSON); otherwise the check fails and
asks for a recapture, rather than comparing whatever variants the two happen to share.

Nothing else in the repository is written. When something differs the build is **kept**: its captures and
`update-report.md`, with the changes at the top, go to `data/bds/<build>`. Otherwise nothing is written. Either way
`data/bds/builds.json` (generated, written through a temporary file) records the build with its protocol, says how a
kept build was kept (`keptBy`: `update` or `history check`) and which kept build an identical one equals (with
`identicalToProtocol` when that build's protocol differs). A later run only checks new builds, so a wider
range is just `--from` an older build. The run stops at the first failure and when the disk of the cache has less than
`--min-free-mb` (1536) left. It removes each build's run and server, the Linux zip it read the inventory from (unless it
was cached before), and the Windows zip of builds that are not kept.

One build keeps its captures per stretch of identical builds. A build whose captures `update` committed (the source of
a bundled data version, referred to elsewhere) is checked too, with `--verify-only` against the previous kept build.
When the two are identical and the record says a history check kept the previous build, the committed build stays and
the other one is replaced: it and every build identical to it are recorded as identical to the committed build, the
record is written, and only then is its directory removed, since only the record refers to it. Captures a history check
kept that the record lacks (a run that stopped in between) stop the next run until they are removed.

A data version stands for the build it was imported from, the build `update` captured, never one a history check kept.
`infer` uses that build's spec capture for its window and lists other kept builds of the window with the same spec data
under `replaces` in `mappings.json`. A kept build of the window with other data is a **gap**: the data version serves its
protocol without sending its data, so it needs a data version of its own (an `import`, decided by hand). `infer` lists it
under `differs` and leaves its capture out, `builds check` prints it, and the build table lists it under Gaps.

What the record says per bundled data version is generated by `builds table` (also run by `builds check`; `checkBuilds`,
part of `./gradlew build`, fails when it is stale): [data/bds/builds.md](../data/bds/builds.md) lists every recorded build
with its protocol, data version and status, and which protocols each data version's builds had; `builds.txt` in the
library lists, per release data version, the build it was imported from and the builds identical to it, never a gap,
which `Paletter#verifiedBuilds` returns. Builds with captures that the record does not know yet count as kept by
`update`. `checkBuilds` also checks the record against data/bds (a kept build has captures, an identical build names a
kept one), and `update` regenerates the table after it captures. `versions.txt` stays written by `import`: it gives each
data version its first protocol, which a preview or a fresh import has before any record does; the table flags a data
version whose first protocol no verified build has.

### Full recapture

The captures of a build answer for the add-on they were made with: the spec add-on is generated from the model, the
fixtures and `bds-feedback.json`, and history checks refuse to compare spec captures of different add-ons. So when the add-on
changes, every kept build has to be captured again, or the model describes some builds with the old add-on and others
with the new one. `recapture.yml` does that in parallel and opens **one** pull request.

**When it runs.** By hand (Actions > Recapture > Run workflow; the `ref` input names the branch to recapture, empty is
the branch the run was started on); on a pull request, by adding the `recapture` label, which recaptures the pull
request's branch and opens the recapture pull request against it (only for branches of this repository, since a fork's
pull request gets no write token; remove and add the label to run it again); and from `bds-data.yml` when the data update's patch changes an add-on input
(`data/model/components.json`, `fixtures.json`, `bds-feedback.json`, `bds-keys.json`), read from git: the pull request of the update was created or updated by this run, and its pushed branch changes one of them against the base: the daily workflow then calls it
on the update's own branch, `bds-data/<channel>`, and the recapture pull request is opened against that branch. A run that leaves the data pull request as it was starts nothing, so a day without news neither recaptures nor force-pushes away a recapture merged into the branch. Nothing
starts it on a push. If both channels change the add-on in one run, only the release one is recaptured; start the
workflow by hand on `bds-data/preview` for the other.

**What it does.**

1. `plan` runs `builds plan`: every kept release build (`data/bds/builds.json`, plus builds with captures the record
   lacks), the newest unrecorded build of each line with a kept build (read from the build list, so a hotfix nobody ran
   `builds check` on is looked at: its leg is compared with the newest kept build of its line, and capture-only keeps
   its captures, which the next `builds check` verifies), and the newest preview with captures in `data/bds`, as a
   matrix. A line is a data version of `versions.txt`: `26.60` is the builds `1.26.60.x` to `1.26.69.x`, since the
   protocol of an unchecked build is not known. A line without a kept build is a new data version, which `update`
   imports. It pins the commit all jobs use.
2. `capture`, one Windows job per build (`fail-fast: false`, at most 6 at a time), runs
   `update --channel <channel> --version <build> --capture-only <dir>`, with the add-on generated from the checked-out
   commit. `--capture-only` is the capture half of `update`: the same captures and the same comparison with the committed
   captures of that build, but nothing is written into the repository; the files that would go to `data/bds/<build>` (and
   `spec/`) are written to `<dir>` instead, and the bundled data, constants, model, white-box and build table are left to
   the next job. A release kept by a history check is recaptured as one (`--against <build>`). The BDS zips are cached
   per build (the daily check's cache keys). The captures and the run's report are uploaded as the artifact
   `captures-<build>`; a failed leg uploads its report and logs, never captures. Under `--capture-only` an `--against` add-on mismatch is information, not a failure (the captures are of the new add-on by design), nothing deletes a directory of the repository, and the Gradle cache is read-only in the capture jobs.
3. `assemble` (only when every leg succeeded: captures of two add-ons never share a pull request) validates the
   artifacts, copies them over `data/bds/<build>/` (overlaying, deleting nothing; a build without committed captures fails,
   so the unchecked build of a line the plan adds fails here: see the open point below) and runs what `update` does after the
   captures, with no BDS: `experiment-marks` (the marks of the bundled versions from the new experiment records), `inferMappings`, `whitebox-coverage` (from the committed `whitebox.json`; the binary did not
   change), `generateComponentApi`, `:paletter:apiDump`, `generateConstants`, `voxel-shapes import` (as `update` does). It also runs `check-mappings --strict` and puts its verdict (residual bits, unclassified wire paths, linked fields) into the report, without failing on it. It fails when the inference changed
   `bds-feedback.json`, `fixtures.json`, `components.json` or `bds-keys.json` (and uploads `git diff -- data/model` as the artifact `recapture-guard-diff`): those captures were made with an add-on that is not the
   final one, so the change is committed and the workflow runs again until a pass changes nothing. It writes a patch of
   the data paths and a report (one verdict line and the collapsed report per build).
4. `publish` applies the patch with the checks of `bds-data.yml` and opens or updates the pull request
   `recapture/<base>` (for the data update of the release channel: `recapture/bds-data/release`), with the report as its body. `assemble` hands over the id of its artifact and `publish` downloads exactly that one.

The builds are not checked against each other again: the set of kept builds does not change in a recapture (that is
`builds check`, which stays a separate step), and each leg compared its capture with the committed captures of its own
build, which is what the pull request shows as the effect of the add-on change. Files that an earlier capture had and the
new one lacks stay in `data/bds/<build>`; the patch has no deletions of them.

**Open: the unchecked build of a line.** `builds plan` adds the newest unrecorded build of each line, but its captures cannot join
the data: the staging refuses a build without committed captures, and staged anyway they stop `inferMappings`, because its spec
add-on differs from the one of the window's import build. The probed keys of `bds-keys.json` apply only to the build they were
probed on (`Fixtures#forBuild`), so 1.26.66.1's add-on lacks the 76 key variants of 1.26.63.1's and numbers the rest differently
(the local recapture of 2026-11-23). A history check of such a build fails the same way. Until that is decided, a recapture runs
without those legs, and `builds check` keeps them unverified.

**Security.** The jobs that run the BDS binary and Gradle over captures (`capture`, and `assemble`, which runs Gradle on
data from the capture jobs) have `contents: read`, no credentials in the checkout and no secrets. Only `publish` has write
permissions and `BDS_DATA_TOKEN`, and it runs no Gradle, BDS or repository script: it applies a patch confined to the data
paths (no other path, no segment starting with `.`, no renames, no links, and every changed path of the working tree checked again). Artifacts
are data: the build names are checked against the plan and strict patterns, the captures may hold only regular files and
directories, every path matches a plain relative-path pattern without a segment starting with `.`, size is capped, and nothing in an artifact is
run. All actions are pinned by commit SHA.

**Determinism.** The capture platform stays `windows` (`CapturePlatform`): the committed captures come from Windows BDS, and
the daily `bds-data.yml` already captures on GitHub's Windows runners, so captures from them have to equal local Windows
captures. That is an assumption of the workflow, not something it proves: the first recapture is best checked against a
local capture of one build (`update --capture-only` with the same inputs, then compare the directories); a difference on
a build whose add-on did not change is a bug to find before the pull request is trusted.

**Cost** (estimates, not measurements of this workflow). A leg is about the time of a `builds check` run, which was about
8 minutes per build locally, plus 3 to 6 minutes of runner start, checkout and Gradle build and the BDS download on a
cache miss: 15 to 30 minutes per leg. With 5 builds today (4 kept releases and the preview) and 6 jobs in parallel the
capture phase takes as long as the slowest leg, then `assemble` takes 10 to 20 minutes (Gradle builds, inference, code
generation): about 30 to 60 minutes of wall-clock time and about 2 to 3 runner hours in total, most of it on Windows
runners. The matrix grows with the kept builds, so wall-clock time stays flat up to 6 builds and then grows by the slowest
leg per 6 builds.

**The trade-off and the merge order.** A change to the model that changes the add-on is complete only with its recapture: merging the model change alone leaves captures of the old add-on next to the new model. So the recapture pull request targets the branch of the data pull request: merge the recapture into `bds-data/<channel>` first (it adds its commit to the data pull request, which then carries model and recapture together), then merge the data pull request into the base branch. Nothing of the model change reaches the base without its recapture, and there is one review of the whole, in the data pull request. In exchange nobody recaptures by hand. If the daily run updates the data pull request between the two merges, it force-pushes the branch and the merged recapture is gone from it; the run then also starts a new recapture, so merge both on the same day.

### Experiments

Bedrock has no list of its experiment toggles, so `update` discovers them (`ExperimentDiscovery`). Candidates are
identifier-like strings from the server binary plus the ids of the committed `experiments.json` records (no hand-written list; `spec-capture` without `--experiments` enables the current toggles of the newest record not after its build). All candidates are written into a fresh world's
`level.dat`; BDS keeps only the keys it knows and logs one code per toggle. Toggles that start game still streams are
current, the others retired. Each current toggle is then captured on its own to attribute content to it.

The result is committed as `data/bds/<build>/experiments.json`, and the bundled version gets experiment marks: per
toggle, the items, blocks and creative stacks it adds, and the items of those stacks none of which carries a block in the
capture with the toggle (`creativeWithoutBlock`; doors, signs, beds): a palette with the toggle sends such an item without a
block, as it does for the items of the regular creative inventory. The bundle itself is captured without experiments.

The record also lists, per toggle, the recipes it adds, removes or changes (`content.recipes`, the recipe diff of the
toggle's capture against the one without experiments). They are not part of the bundle's marks: the recipes module
bundles them. A history check does not count a toggle's recipes as a difference when the earlier record lacks them (none of the
committed records has them yet: [Recapture to-do](#recapture-to-do)). `recipes-capture` refuses a build without captures in
`data/bds` and a machine of another BDS platform than the committed captures.

### Experiment gating of components

`@BedrockExperiment` and the experiment notes of the generated component Javadoc come from the creator docs (`experiments` in
`components.json`). `spec-capture --gating` (run by `update` after the spec capture, on the same server) verifies them per build:
it loads an add-on with only those components (`GatingCapture`: a base and a control without the component each, derived from the same
model data) in a world **without** experiments, and writes `data/bds/<build>/spec-gating/gating.json` (generated, marked). Per
component, `without` is `rejected` (an error in the content log, or the file not sent), `ignored` (BDS sent the same as the control) or
`accepted`; `with` is what the spec capture of the build, whose world has the experiments on, did with the same base. The codegen
reads the files (`Gating`): the Javadoc says "BDS-verified" for the builds where a component is gated, names the builds where BDS takes it
without any experiment, and the builds where BDS rejects it even with them on; `generateComponentApi` prints the components rejected with
experiments on in every captured build (they are kept, only reported; the update report lists them too). The capture is not essential: a build
without the file leaves the gating "unverified against BDS", never a failure (no build has the file yet: [Recapture to-do](#recapture-to-do)). The docs name one entry for `collision_box` (Holiday Creator Features and Upcoming Creator Features), which is captured at the
current format; the Holiday Creator Features form of an older format is not a variant of its own.

### Recipes

`recipes-diff` diffs two committed recipe captures in `data/bds`, normalised (list layout, net ids and random UUIDs ignored): recipes
added, removed and changed, mixes, trims. `update` reports the same diff, and checks that recipe items, tags, block states and net
ids hold (a FAIL when one does not). A run whose own capture has no `crafting_data.json.gz` fails, and so does an unreadable recipe
capture; a build without a committed recipe capture is only not compared.

`recipes-import` writes the recipe captures of `data/bds` to the bundled
`paletter-recipes/src/main/resources/paletter/recipes/<data version>.nbt` (item identifiers and aux values as BDS sent them, no net
ids, no random UUIDs; the trim patterns and materials are in the bundle but not in the API) and `RecipeStations` (a constant per
station tag of the captures, in `paletter-recipes/src/generated`). A capture belongs to the data version of the protocol in its
build's `experiments.json`. The import fails for a recipe kind or ingredient descriptor the bundle has no place for, an item that is
not in the palette of its data version, an unknown unlock context, a malformed UUID, and a container mix with an aux value or an
empty block state or tag.

### Previews

Paletter bundles the newest preview next to the releases. `update --channel preview` imports it like a release, marked
`preview` in `versions.txt`; the library serves it only to a Paletter built with `Paletter.builder().previews(true)`. A
preview newer than every codec of the protocol library is captured with the newest codec: `import` then reads its
`codecProtocol` from the capture's `capture.json` and writes it as `codec=<protocol>` on the version's line
(`DataVersion#codecProtocol()`), e.g. `26.70 2259 preview codec=2225`. Generated API that only the
preview has (constants, states, enum values, components and fields BDS releases reject) is marked
`@SincePreview("<version>")` and is kept out of `constants-history.json`. Importing a newer preview, or the preview's
release, drops the bundled preview and its `data/bds/<build>` captures. Release runs never compare against a preview's
captures.

### Other sources

`verify --source DIR --data-version 26.60` diffs a directory in the CloudburstMC/Data layout (Geyser's file names work too)
against a bundled version: block states and order, hashes, items, components, data driven blocks and the creative
layout. It writes only a report.

`export --data-version 26.60 --out DIR [--previews] [--all-experiments]` writes what a compiled palette
(`Paletter.bundled().vanilla(version)`, or with `--all-experiments` the palette with every experiment toggle on) sends, in the
file formats of CloudburstMC/Data (which dumps a world without experiments, like the export without `--all-experiments`): `block_palette.nbt` (states in registry index order, each with its
runtime id as `network_id`), `runtime_item_states.json` and `item_components.nbt` (the item registry),
`creative_items.json` (the creative content) and `data_driven_blocks.nbt`. A `_generated` file marks the directory as
generated. The files are not byte-comparable with cb/data (gzip, key order, JSON layout, item order); compare with
`verify --source <cb/data> --data-version 26.60 --against DIR`, which runs the engine of `verify --source` with the export as the
compared side: positions exact, items by identifier, `version` tags ignored, plus a section checking the export's
`network_id`s against the hash of each state and against cb/data's. `CloudburstDataTest` runs the same
comparison in the normal build for every bundled release, against cb/data files committed in
`tools/src/test/resources/test-data/` (see `docs/updating.md`).

Vanilla block palette order cannot be observed from the Script API or the network, which is why bundled palettes still
descend from CloudburstMC/Data and Geyser files and are verified against BDS rather than generated from it. The
bedrock-samples metadata and the BDS `definitions/` folder are not used: they miss items, lack defaults or order, or
hold nothing Paletter needs.

## The component model

The custom item and block API mirrors Bedrock's add-on components. Its model is built only from the official creator
docs and from what BDS does.

```
./gradlew :tools:generateModel [-Pdocs=<minecraft-creator checkout>]  # docs -> components.json
./gradlew :tools:generateAddon                                         # spec add-on -> tools/build/spec-addon
./gradlew :tools:run --args="spec-capture --channel release"           # run it on BDS -> data/bds/<build>/spec
./gradlew :tools:inferMappings                                         # -> mappings.json, coverage.md, bds-feedback.json
```

**Docs.** `DocsParser` reads the component pages of MicrosoftDocs/minecraft-creator at a pinned commit into
`components.json`: per component its fields, types, defaults, enums, ranges, format versions and experiments.

**Variants.** The spec add-on has, per component, a control, a base with every required field set, and one variant per
field value. Values come from the field's type: limits and one past each, enum values plus an invalid one, empty and
wrong-length lists, and so on; where the text of a map's entries matters (the Molang of `bone_visibility`), `fixtures.json`
`mapValues` lists the values to try. Limits come from the docs and from `bds-feedback.json`, which records what BDS's content
log said last time; where BDS's bound differs from the docs' it comes first and the docs' bound is tried too (`coverage.md`
marks such a range as disputed). `spec-capture` and `infer` are repeated until that file stops changing. When BDS rejects a variant
for a member it does not vary, `spec-capture` shrinks the variant and captures again.

**Samples for the rules.** The rule kinds of the mapping inference (`rule/`) need samples the one-field-at-a-time variants lack; the
generator adds them, and `SamplesTest` checks each against a model of its own and against the committed one (schema on):

- *Pinned values.* `MAX_VALUES` cuts only unpinned values. Pinned are every value of a schema enum (so the table of an enum is
  complete; `Schema#enumValues`; `fixtures.json` `unpinnedEnums` lists the ones left out, with the reason: an open enum is a string in the
  API, and a test keeps the two lists in step), the probes and the samples below. The `use_animation` names come from the schema enum
  and are not hand-listed.
- *Molang* (`bone_visibility`): the `mapValues` strings under three keys (`bone`, `bone_2`, `bone_3`), twice shifted so that each string is under
  two keys; each as the `expression` of the object form `{expression, version}`; and numbers. The element types and members come from the schema
  (`bone_visibility{}`), the strings from `mapValues`; without the schema the model knows only the string.
- *Names in a hash ordered list* (`uv_lock`): `fixtures.json` `listNames` gives five names; the list is written in every order of the first
  three, in two more sets of three (written and reversed) and with all five (written and reversed), so that BDS's order is told from the written
  one and from a reversal.
- *Packed bits* (`material_instances`, `fixtures.json` `boolCombinations`): the booleans of each face object in every combination
  (`face_dimming`, `isotropic`: 4; with `alpha_masked_tint` and the members it needs: 8), so each bit is seen alone and in pairs.
- *Boxes*: an object with the vectors `origin` and `size` is also written with both varied together: nine boxes in which each axis takes every
  combination of three origins and three sizes (never negative), inside BDS's `box` limit of the component (`bds-feedback.json`
  `box origin size ...`, which BDS reports on the component). A component without that fact yet also gets one box past any limit
  (`(past any limit)`), so that BDS says its limit and the next `infer` records it; until then its boxes stay inside the tightest limit
  of the other components: **borrowed, unverified** for it ([Recapture to-do](#recapture-to-do): `collision_box`; a test checks the fallback).
- *Vectors* the schema also describes by `x`, `y`, `z` stay vectors in the base (as an object they would have no member without a default).
- *Fractions not exact in binary* (`fixtures.json` `probeValues` of a number field): `use_modifiers.use_duration` 0.35, 0.7 and 0.95, which
  its linear rule scales by 20 onto an integer, so the capture says how BDS rounds the product.
- *Two components onto one leaf* (`fixtures.json` `combinations`, role `combination`): whole component maps that put a component next to
  another one writing the same wire leaf (`wearable`'s slot table with `max_stack_size` and with `allow_off_hand`, disagreeing on the
  leaf, in both orders of the file), so the capture says which value BDS keeps (`SharedLeaves`).

**Enums of an old format.** BDS's schema lists some enums only for format 1.26.30 (`swing_sounds`, `use_modifiers.start_sound`,
`durability_sensor.durability_thresholds[].sound_event`, ...): the add-on's newer definitions take any string there, so their values are not
varied. Deliberately: they are sound event names, which no palette feature needs.

**Script API module.** The beta add-ons (`behaviour-dump`) depend on the `@minecraft/server` beta of the build. `update` reads the versions from
the `script_modules` of BDS's own documentation generator (`ScriptModules.parse`) into `data/bds/<build>/script-modules.json` (marked
generated); `behaviour-dump` reads that file, and a build without it fails: nothing looks it up on npm. The layout of `script_modules` is
read as `@minecraft/server/<version>` or `@minecraft/server_<version>` and is unverified against a real tree (none is committed): a run that
finds no version fails and says what it found. No build has the file yet ([Recapture to-do](#recapture-to-do)).

**Probes.** Values that no docs text or BDS message lists, but that a hand table of `Transforms` holds, are tried too: `fixtures.json`
`probeValues` gives a field further strings (the formatting colour names of `hover_text_color`, which no schema enum lists), and `descriptorValues` gives every block descriptor field real vanilla blocks with enum, boolean and string
state values. They are probes, not facts: only what BDS accepts and sends is evidence. `spec-capture` also keeps the ERROR and WARN lines of the content log
in the order BDS wrote them (`content-log.raw.txt`) beside the sorted `content-log.txt`, so that a line can later be attributed
by the lines around it. Every line must name a variant of the add-on (its file, or its quoted identifier) or be one of the phrasings
in `SpecCapture.UNATTRIBUTED`, which lists the lines committed captures recorded about no single variant. Any other line fails the
capture with the line quoted: a reworded error would otherwise name no variant and count it as accepted.

**Linked fields.** One field at a time is not enough where BDS ties two fields: `damage_chance.max` below the default
`min` is refused, `replace_block_item` is ignored unless `block` is the item itself. The content log says so, and
`bds-feedback.json` keeps it as a link: `order <low> <high>`, `conflicts <path> '<value>'`, `identifier <path> <kind>`. Beside each
variant of such a field the generator adds a linked one (label `<label> linked <paths>`): the other field at its far
limit, at its second valid value (`fixtures.json` `alternatives`), or the variant's own identifier with a minimal block of
that name. The plain variant stays, so BDS keeps saying what ties the fields. The API refuses what BDS refuses: the record of
the object checks an `order` and a `conflicts` fact in its constructor.

**What BDS says that the docs do not.** BDS wins over the docs. Type errors in the content log become errata.
`spec-capture --probe-keys` asks BDS about keys the docs leave out, using candidates from the BDS binary, the bedrock
wiki and vanilla packs (only as names, never as values); accepted keys land in `data/model/bds-keys.json`.
`spec-capture --format-sweep` captures components at the `format_version` boundaries, as evidence for hand transforms.

**Inference.** A variant is accepted when BDS sent it and logged no error. For each field, every wire leaf that changed
against the base is explained by the first rule that fits all observations: `identity`, `linear`, `table`, `affix`,
`bitset`, `ordered-set`, `element`, or a constant switched on by the field's presence. Three more kinds explain what a
table or an identity cannot: `packed-bits` (a boolean that is one bit of a leaf several fields share, `packed_bools`),
`molang` (an expression BDS sends with its numbers in six decimals) and `hash-ordered-set` (names BDS sends ordered by
the hash of each). Each needs evidence a few captured values cannot fake (an observation without the field, two numbers
and a fraction, lists in more than one order); until the add-on provides it the field stays with its hand transform.
`whenAbsent` records what BDS sends when the field is omitted. Fields no rule explains need a hand transform. Captures from different builds that
differ become separate protocol windows in `mappings.json`. What a linked variant's other field moves on the wire is
not attributed to the field it varies.

A rule has to hold for values the capture did not try. A value table and an `ordered-set` in an order of BDS's own
are fitted only for a closed set of values (an enum), all of them seen: for a list of any strings the order of the
few captured ones says nothing about the others. A leaf only the list form of a field sends is not explained by the
scalar form not sending it.

A field BDS accepts whose value no rule follows (nothing on the wire moves, or only its presence does) is `dropped`
(server only), unless the messages of its variants name another field or quote its value: then it is `linked`, as the
other field may have decided what BDS sent.

The inference fails `check-mappings --strict` and `update` on integer bits no field explains, on wire paths that
are neither mapped nor classified, and on `linked` fields (capture again: the generator links them; if it already did,
the field needs a rule or a hand transform). [data/model/coverage.md](../data/model/coverage.md) lists the result per
component, including fields that need a hand rule and hand transforms BDS has not verified.

`ComponentConformanceTest` rebuilds every variant BDS accepted through the generated API and compares Paletter's NBT
with BDS's, for every captured build. It has no list of exceptions: a variant the API cannot express, or encodes
differently, fails the build. Such gaps are closed in the model (`api.json` `optional`, `openEnums`, `unions`, `forms`,
protocol windows) or with a hand transform, never waived.

## White-box discovery

Captures show what BDS sends for the add-on it is given. They cannot show a component nobody wrote a variant for, a
key that only a rare input switches on, or a component the docs do not mention. The code of BDS can: `whitebox` reads
the public server binary of a build, without running it, and lists what the code is able to send. `whitebox-coverage`
then names what no capture of that build shows. `update` runs both (see "In `update`").

```
./gradlew :tools:run --args="whitebox --version 1.26.63.1"      # -> data/bds/1.26.63.1/whitebox.json, and the diff to the build before
./gradlew :tools:run --args="whitebox-coverage"              # -> data/bds/<build>/whitebox-coverage.md for every build with a whitebox.json
```

The facts are used to direct captures and to notice changes, never as data: the component model still learns every
shape from a capture. Only facts leave the binary (names, flags, keys, kinds); no code does.

### What it finds

`whitebox.json` (generated, per build):

- `itemComponents`, `blockComponents`: every registered component with `network` (is it sent to the client), `kind`
  (`reflection`: written by BDS's generic schema writer; `hand-written`: by code of its own; `mixed`: both; `not-sent`),
  `writes` (the keys and string values the hand-written writer mentions), `writesExtra` (those of a second writer that
  some classes have, such as the four geometry flags), `writesNested` (those of functions the writer calls, such as the
  block and item descriptors), `reads` (the reader's), `types` (the NBT type stored after a key), `schema` (the keys of
  the reflection schema, where one function registers the component alone), `hooks` (virtual functions after the reader
  that only this class has) and `code` (a checksum of what the writer does, to notice a change that adds no key).
- `itemClassesWithoutName`: classes of the item family that are constructed elsewhere than in the registration, such as
  the component BDS adds for a script `onUseOn` callback.
- `traits` and `envelopes`: the same for the block traits and for the code that writes `item_properties` and the block
  definition around the components.
- `layout`: the virtual function slots it read the above from; `notes`: what it could not resolve.

### How it finds it

The discovery needs no symbols and no type names. It relies on how the code is built, and fails rather than guess when
an anchor is missing:

1. Functions come from the unwind tables, pointers in data from the relocations (Linux) or the read-only data
   (Windows).
2. A component is a class with virtual functions. Block components return their name from a virtual function that
   only returns a static string; every table of function pointers that has such a function is a candidate, and
   `minecraft:geometry` anchors the family. Item components are named by the one function that registers them, found
   through `minecraft:max_stack_size`: it mentions each name and constructs each class in turn.
3. In the anchor's table, the first function that returns a constant and is followed by two functions with real code
   is "is this sent to the client"; the next two are the writer and the reader. All classes of a family share that
   layout, so the slots are found per build and never written down.
4. A writer that mentions no key and uses the one writer class that all such writers share is `reflection`. The
   functions that hand-written writers hand their keys to (and that no reader calls) tell a second writer from a
   reader.
5. Keys are string literals, or short strings that the compiler builds in place with a few instructions
   (`Listing` follows those). The Linux build also stores each tag's type right after its key.

Class names are added as `class` where the build has type information (Linux releases), as a label only.

| Build | Result |
|---|---|
| Linux release (type names) | everything above |
| Linux preview (no type names) | the same, without `class` |
| Windows | block components, traits and envelopes as on Linux, without tag types; item classes are found with their kinds and keys but cannot be paired with their names, so `whitebox.windows.json` is a cross-check only |

What it cannot know: values, defaults, list and compound shapes, which input switches a key on, and the keys of
reflection components whose schema is registered together with others. A literal may be a string value (`water`,
`opaque`) rather than a key.

Items of the legacy format (most vanilla items, and add-on items of old format versions; their data has no
`item_properties`) are sent under the keys of that format, and some of those are not component classes:
`minecraft:foil`, `minecraft:seed`, `minecraft:use_duration`, `minecraft:camera` and `minecraft:block` are handled by
the code of the legacy item format, not by a registered class. `whitebox` does not list them, and the self-checks do
not ask for them.

### Coverage

`whitebox-coverage` compares `whitebox.json` with every capture of the same build (`spec`, `spec-format`, `spec-keys`,
the vanilla capture's data-driven content) and writes `whitebox-coverage.md`, the gaps:

- a component that is sent and was never captured;
- a key or string value a writer mentions that no capture of its component has;
- a key that every capture has with the same value: a branch of the writer that was never seen (`replaceBlockItem`,
  `molangVersion`, a trait's `place_behavior`).

A gap closes with a capture: a new variant in the spec add-on, a format sweep entry, or a probe add-on. Some never
close (a value BDS writes as a constant, a literal that is not sent) and stay listed; the report is the place to see
them, there is no list of exceptions.

`whitebox-coverage --check` fails when a committed report is not what the committed facts and captures give, so the
list cannot drift from the data. `--strict` fails on any gap; it is opt-in, as some gaps never close.

### Script custom components

Read once from a probe add-on on 1.26.63.1 (a script module that registers one custom component per callback, used by
blocks and items in both JSON forms; its raw data is not in the repo) and matching what `whitebox` reads from the code.
The spec add-on now captures it (below); until a recapture has run ([Recapture to-do](#recapture-to-do)), treat these rules as documented, not captured:

- Blocks: `minecraft:custom_components` is sent as three bytes, `hasPlayerInteract`, `hasPlayerPlacing` and
  `isV1Component`. Component names and parameters are never sent.
  - The old form (`"minecraft:custom_components": ["ns:name"]`, block format versions up to 1.21.80) sends 1, 1, 1
    whatever the script registers.
  - The new form (`"ns:name": {parameters}` as a component key) sends `isV1Component` 0, `hasPlayerInteract` 1 only if
    one of the block's components has `onPlayerInteract`, and `hasPlayerPlacing` 1 only if one has
    `beforeOnPlayerPlace`. The other callbacks change nothing on the wire.
  - From format 1.21.90 BDS drops the old form with a content log error, and from 1.26.20 it rejects the block.
- Items: the custom components component is not sent. A component with an `onUseOn` callback makes BDS add
  `minecraft:publisher_on_use_on: {autoSucceedOnClient: 1b}`; no other callback changes the item's data.

The spec add-on has a script module (`@minecraft/server` 2.0.0, one pinned version for every build) that registers, on
`system.beforeEvents.startup`, the components of `scriptComponents` in `fixtures.json`: per kind one without callbacks,
one per callback BDS is documented to put on the wire, and one with every other callback of that module version (names
from its `index.d.ts`). The variants (role `script`) use them in the old form at format 1.21.80 and in the new form
at the current format, with two components on one block, with parameters, in a permutation, and next to the placers
(which also write `publisher_on_use_on`). `spec-capture` fails when the script did not print `PALETTER-COMPONENTS`,
so a script that did not load cannot pass for components without callbacks. Open until captured: whether the block's
compound is sent with neither callback, what happens in permutations, with a name the script did not register, and
whether an `onUseOn` component together with a placer sends 1 or 0. The API (`ScriptHooks`, `UseOnHook`) offers only
the new form, so the conformance test does not compare the old-form variants.

### In `update`

`update` runs it after the captures and never depends on it. On the build's Linux zip it reads the facts, checks them,
stages `whitebox.json` and `whitebox-coverage.md`, diffs against the build before and puts what needs a human under
"Needs attention": `!` lines (a new component, a changed network flag or kind, a key that came or went), each naming
what to capture again, and the gaps the committed report did not list. `~` lines (the writer's code changed, its keys
did not) stay in the collapsed part.

Safeguards, so that it can never break an update or go quietly wrong:

- An exception or a failed self-check is a FAIL row, "white-box unavailable for this build: <reason>"; `whitebox.json`
  is staged only after a pass, and everything else of the update goes on. The self-checks (`WhiteboxChecks`): every
  component the build's captures show is found (the keys of legacy format items aside, see below), and no more than 3
  components or keys (or 2%) that a capture of the build still shows are lost against the build before. What no capture
  shows may go; it is a `!` line of the diff. Docs-generator schemas are not read yet; the captures and the build before
  stand in for them.
- CI (`:tools:checkWhitebox`, in `check`) compares committed reports with committed facts and captures, never the
  binary; `--strict` is opt-in and a gap is a line in the report, not a red build. `:tools:whiteboxRegression` (not in
  `check`) runs the analysis on a cached zip and compares it with the committed facts, and skips without the zip.

What stays capture-based: every shape, type, value and default; the order of keys; which JSON produces what; the
versions at which behaviour changes (the format sweep); everything `mappings.json` and the conformance tests hold.

## Code generation

### Component API

`./gradlew :tools:generateComponentApi` writes the component classes in `item.component` and `block.component`, the
sealed `ItemComponent`, `BlockComponent` and `BlockTrait`, and the encoders in `internal.component` (`ItemWire`,
`BlockWire`, `TraitWire`, `ComponentIndex`, `TraitStateTable`). The generator lives in its own `componentApi` source set,
so it runs even when `paletter` does not compile.

Inputs, all in `data/model` except the last:

- `components.json`: components, fields, defaults, docs text.
- `fixtures.json` (hand): errata, samples, `replacedBy` with evidence. An erratum holds only what BDS's schema does not give
  (its `schema` member says why): `HandInputTest` fails on one without which the merged model is the same (`Fixtures#redundantErrata`).
- `bds-feedback.json`: required fields and ranges BDS enforces, which win over the docs.

  These three and `bds-keys.json` are read as one model, built once (`Fixtures#apply`) for the add-on generator, the
  inference and this generator: the docs, then the errata (an erratum's types first), then what BDS said.
- `mappings.json`: per component and protocol window, how each field reaches the wire. A component is
  `{"windows": [{"protocols": [...], "status": ..., "fields": ..., ...}, ...]}`, oldest window first, read only through
  `MappingWindows`. A field keeps what the generators read (status, rules, absent values, transform, `unknownToBds`);
  what only explains it (accepted and rejected counts, `bdsErrors`, `rejectedValues`, `bdsRange`, `unexplained`) is in
  `mappings-evidence.json`, the same windows (`MappingEvidence`), written with it by `infer` and compared by
  `check-mappings`; `coverage.md` is made from the result before the split. Every window protocol of the captures must be in some window of a captured component (a capture
  without it fails generation); the oldest window also holds below the oldest capture. A field with no result in the
  newest window (`not-generated`, its capture lacks the field's variants) while an older one has one is reported by
  generation (a `warning:` line): its API facts (required, limits, defaults, the history's wire) come from that older
  window, and protocols from the newest window on leave it out with a report entry until a capture with the current
  add-on. Reported, not failed: the gap is the capture's, and failing would stop every generation until the recapture.
- `api.json` (hand): Java shape only (names, unions, value forms, open enums).
- `HandTransforms` (hand, in the tools): which fields are compiled by a method of `internal.component.Transforms`.
  Each method's Javadoc says why no inferred rule fits and what evidence backs it.
- `api-history.json` (generated, read and rewritten by every run): every Java name the generator has emitted, by a stable
  identity: component id for a class, `<component id>:<JSON path>` for a nested class, value class or field (with the
  wire leaves the newest capture with a result for it writes from it, and its model `type`, `nullable` and `default`), `<id>:<path>=<value>`
  for a constant. A recorded name is reused, never recomputed: a docs restructure or a new component renames nothing (a
  new collision gives the `Block`/`Item` prefix to the newcomer). When a field's path leaves the model and exactly one
  new field of the same object writes the same wire leaves, the JSON key was renamed: the old accessor and builder setter
  stay as `@Deprecated` delegates, and the entry records `renamedTo`, which every later run follows directly. When no
  field matches by wire leaves (the entry has none, or Bedrock renamed the NBT key too) and the same object gained a
  field, generation fails until `api.json` decides: `renamedFields` (`{"<old identity>": "<new identity>"}`) or
  `removedFields` (a list of old identities). Without such a field the entry is marked `removed` and keeps a `@Deprecated(forRemoval = true)` stand-in (`StandIns`): an
  accessor that returns the field's default and a builder setter that does nothing. A component that leaves the model
  is marked `removed` the same way and keeps a stand-in class, which every palette leaves out with a report warning.
  Generation prints a `warning:` line for each stand-in; two candidate successors fail. Entries are never dropped (a
  test holds the committed file to that): a stand-in goes only when its entries are deleted deliberately, in a major
  release. A name in `api.json` must agree with the recorded one, so a deliberate rename edits both. The recorded
  `type` and `nullable` of a live field lock its Java shape: a field whose type (the nested class it uses included) or
  nullability would change fails generation, naming the field and both shapes. Keep the old shape through `api.json`,
  or, for an intended break (a major release), set the entry's `type` and `nullable` to the new shape.

Rules the generator follows:

- Defaults are the documented ones, unless BDS sends something else for an omitted field; then the field stays unset
  and the encoder writes BDS's value.
- Components and their objects are final classes with a private constructor, record-style accessors and a builder, not
  records; documented string values are open value classes (constants, `of(String)`, `isKnown()`), not enums
  (docs/api.md, "Evolution"). An exhaustive value table of the encoder switches over `value()` and leaves a newer value out
  with a report warning.
- Required fields are checked in `build()`; ranges and step sizes in the private constructor, which every factory and
  builder goes through.
- Public Javadoc names Bedrock data versions, not BDS builds: "Range [1, 54] (Bedrock 26.60)", never a build number or a
  `data/bds` path (`Docs#bedrock`; the evidence stays in the model). The protocol windows the hand transforms compare with
  are `ComponentIndex.V26_60` and so on, named by data version too.
- A field with no rule in a protocol window is dropped there with a report warning.
- `@ServerOnly`, `@Deprecated` and `@ReplacedBy` come from the data: the windows' status, the docs status, BDS's
  rejection message, or a `fixtures.json` `replacedBy` entry.
- Every component in the docs is generated, including ones BDS never sends. Components that cannot be generated are
  listed with the reason in the Javadoc of the sealed interfaces.
- A field that takes several JSON forms (`uv_lock`: boolean or bone names; `default_color`: RGB channels or hex;
  `repair_amount`: number or Molang; `repair_items[].items`: identifiers or a tag query; a face of `material_instances`:
  instance or alias) is one value of a sealed type, written from `api.json` `unions`: `name` of the type and `variants`
  (JSON type to the record name, or `{name, doc}` where `doc` says what the form means). Fields with the same type name
  share the type, so the three geometries have one `UvLock`; two shapes under one name fail the generation. The type is
  a file of its own in the package of its components, or nested in the component when a form is one of its types
  (`MaterialInstances.InstanceOrAlias`). It has one record per form (`value()`) and a factory named after each form
  (`UvLock.flag`, `UvLock.bones`; `ItemsOrTags.items` also takes vanilla constants). Its builder setter has an overload
  per form, a list as `(first, rest...)` (never empty, primitives stay primitive), except for the forms `noOverload`
  lists: a string that is an alias or a query is no obvious value (`all("x")` would read as a texture), so it is set as
  `all(InstanceOrAlias.alias("x"))`. The keyed extra map of a component refuses the keys that have a field of their own.
  The form is told by the type of the value, never a runtime check: a hand transform switches over the type. The union
  also permits a sentinel class that is not public (`FutureUvLock`), so every switch over it needs a `default`, users'
  included (docs/api.md, "Evolution"); a new form is found by the conformance test, not the compiler. The sealed
  component interfaces have one too (`FutureItemComponent`). A union field still needs a hand transform for its wire encoding (the
  generator fails otherwise) until the type-dispatched rule kind exists.
- Generation fails on two mappings for one protocol, name collisions, two fields writing one wire leaf, or an
  ambiguous union.

### Behaviour keys

The same task writes `BlockBehaviour`, `ItemBehaviour` and `internal.behaviour.WireRules`, which reads a key from the
component data of a custom block or item. The hand-kept table `BehaviourKeys` in the tools names each key's type, Javadoc,
BDS sources and, for keys custom content sets, its component field. The field's rule in `mappings.json` is read
backwards; where the behaviour probe measured engine values against component values (friction), the fitted relation
converts them. Shapes use the hand-written `internal.behaviour.ShapeRules`.

### Vanilla constants

`./gradlew :tools:generateConstants` writes `BedrockBlocks`, `BedrockStates`, `BedrockItems`, the enums in
`vanilla.state`, with what only a bundled preview has marked `@SincePreview`. Inputs: the newest bundled release and
preview, `renames.txt` and `data/model/constants-history.json`, which records every constant ever generated so
regeneration cannot drop one. Commit the history together with the classes.

- Names are the UPPER_SNAKE of the identifier path. A state and a state enum keep the name `constants-history.json`
  records. A new name that is invalid or collides fails generation until the hand-written
  `data/model/constant-names.txt` names it (`blocks|items|states|enums <key> <name>`; a line that matches nothing in the
  data fails generation too).
- A state keeps its type and enum; a state that changes kind fails generation.
- Removed content stays as a deprecated constant (plain `@Deprecated(since)`, never `forRemoval`): an alias where the
  identifier moved (following chains of renames to the final constant), otherwise resolving to `minecraft:unknown`.
- `@since` is the Paletter version that added the constant, in every class. The Bedrock release is the line
  `First in Bedrock <release>`: the first bundled release that has the content without an experiment, from
  `data/bds/<build>/experiments.json` (captures of a preview do not count for a release). It is derived on every
  generation; the history keeps one only if its release is no longer bundled. Content that already existed before the oldest
  bundled release (26.30) has no such line (and no `bedrock` in the history): `data/model/baseline-26.20.txt` lists the block and
  item identifiers of the release before it, from CloudburstMC/Data commit `eb77f9f` (v975; Apache-2.0, only identifiers kept).
  `baseline --source <checkout at that commit> --data-version 26.20 --commit eb77f9f` writes it. Content gated by an experiment in 26.30
  that a later release ungated keeps the later release.
- `internal.vanilla.BlockLayout` checks that each block's states are the full cartesian product of its values, so state
  ids can be computed from strides.

### Block definitions

The vanilla block states of the bundled versions are generated code, not data. `./gradlew :tools:generateBlocks` (`blocks
generate`; checked by `:tools:checkBlocks` in `check`) writes `dev.opencollab.paletter.internal.vanilla.blocks` with JavaPoet
(`BlockCode` in the tools):

- `BlockValues`: every value list of a block property once, the values in Bedrock's order: `CARDINAL_DIRECTION =
  StateValues.strings("minecraft:cardinal_direction", "south", "west", "north", "east")`, `AGE_0_15 = StateValues.ints("age", 0, 15)`,
  `OPEN_BIT = StateValues.bool("open_bit")`. The name is the property's without `minecraft:` (with it where two properties would
  share one, `MINECRAFT_FACING_DIRECTION`), an int property adds its range, a string property with several value lists the number
  of its values and the first (`COLOUR_2_GREEN`). Ints that are no run are listed (`intList`); byte values other than false then true fail generation.
- `BlockBase`: the oldest version of `versions.txt`, one line per block: its identifier, its properties in the order Bedrock
  enumerates its states (the first changes slowest, the last fastest) and its default state where that is not the first:
  `v.block("minecraft:copper_chest", CARDINAL_DIRECTION).defaultState("north")`.
- `BlockChanges<version>`: what changed against the version before. The class names once what the version was imported from
  (the builds `builds.txt` verifies for it, the import build first; a preview has none). Each line says what it changes: a new
  block (`v.block`), a removed one (`v.remove`), properties inserted into a block's order (`v.addProperties(block, position, ...)`,
  0 the slowest), a removed property (`v.removeProperty`), a new default (`v.defaultState`); anything else (other values, another
  order) redefines the block (`v.redefine`) with what changed.
- Provenance of the order: BDS sends no palette. A line that gives a block of several properties a state order (and a block of
  the base) says `state order confirmed by CloudburstMC/Data` where the CloudburstMC/Data palette of the version in
  `tools/src/test/resources/test-data` has the block's states in the same order, else `state order inferred, not observed`: the
  order `update` inferred (`ReferencePalette#keyOrder`). `generateBlocks` prints those blocks, `update` lists them as a decision.
- `BlockData` builds them all for `VanillaBlocks` (hand-written, `internal.vanilla`), which loads it by name: the library
  compiles without the package.

What is derived, at palette build (`BlockDefinitions#derive`), and never stored: the states of a block as the full cartesian
product of its values (an odometer, the last property fastest), the keys of each state sorted, the blocks ordered by the
unsigned FNV-1 64 hash of their identifiers (`BlockRegistry#nameHash`), so the sequential runtime ids, and the hashed ids
(FNV-1a of the state NBT, `BlockHashes`, as before). The generator reads each version's palette (from the version file where
it still has its block states, as an import writes it, otherwise from the definitions the tools were compiled with), reads
the definitions from it (each property's place from how often it changes) and derives the palette again through the same
code the library runs: it fails with what it found, never a guess, on a block whose states are not one run, not the full
product of their values or in no odometer order, a property order that is ambiguous (two properties that change at the same
rate), blocks out of name hash order, a state whose keys are not sorted, or other defaults. Properties of one value never
change, so their place cannot change the states: they go first, by name. Then it applies each version's changes to the version
before and fails unless that gives the version. It writes the sources and every version file without its block states
(`blocks` and `block_defaults`, which the codec then takes from the definitions) but with `blocks_digest`: the state count and
an FNV-1a 64 over the hashed ids of the states in order and of the defaults, of the palette that was imported. Reading a file
without block states (`checkBlocks`, every tool, a directory data source) fails, naming the version, unless the derived palette
has that digest. The bundled data source skips the check at load (it costs a cold load about 60 ms): the build checks the
bundled files (`checkBlocks`, `PaletteDataCodecBlocksTest`). So a hand edit of the generated classes, a merge of two data changes into a chain nobody captured, or a file paired with
the definitions of another library cannot pass silently. `blocks export --out <dir>` writes the bundled data with every
version's block states again (to recover, see updating.md troubleshooting).

`import` runs it after writing the version. `update` runs it on the staged data (`BlocksStage`, after the constants) and stages
the sources; the version files go into the repository with their block states, because the stages after that (the spec capture,
the shape import) read the bundled data in the same process, whose compiled definitions do not know a palette that is new or
changed in this run. Writing them without block states is the very last step of the run. `PaletteDataCodec#write` leaves the
block states out on its own wherever the definitions of the version give exactly them, so rewriting a version file (experiment
marks, a refreshed version) keeps it slim, and a version whose palette changed keeps its states until `generateBlocks` folds them
in. Data of a version the library has no definitions of (a directory data source) keeps carrying its states.

What stays data, and why:

- Per version file (`<version>.nbt`): the items (ids are BDS registration order with holes; an update shifts 45 to 584 of them),
  the creative inventory (about 2,000 ordered stacks, the block a stack carries exactly where BDS sends one), item tags, experiment
  gating and the block to item relation. Of the relation only what is not derivable is stored: `block_items` holds the blocks
  whose item has another identifier (about 190 of 1,500), `blocks_without_item` the blocks no item places; every other block is
  placed by the item of its own identifier.
- `properties.nbt`, stored once with version ranges: item component data (a tree per item; 20.7 KB gzipped for five versions,
  16 to 17 KB per version if each version file held its own), the property data of the vanilla data driven blocks (6.2 KB) and the
  order BDS sends those in (`block_order`: neither sorted nor by name hash or block id, so data). None of it is derivable, and the
  ranges are what keeps it small; the typed component API would be the code form of the trees, which is a project of its own.

Retiring a version (`retire`, [updating.md](updating.md) section h): once its `versions.txt` row and file are gone,
`generateBlocks` makes the next version `BlockBase`, with what it inherited folded in, and drops its change class.

Tests: `BlockCodeTest` runs the generator on three small versions (what the classes say, that the compiled output gives every
palette again, retiring, splitting); `BlockModelTest` has the palettes it must refuse; `BlockGeneratorTest` runs it end to end on
a repository of its own (sources, slimmed files with their digest, `builds.txt`, the second source, export); `BlocksStageTest`
runs the update stage that way, for a new version and for a changed palette under an existing name; `BlockDefinitionsTest` and
`PaletteDataCodecBlocksTest` in `:paletter` test the runtime and the format. `GeneratedBlocksLimitsTest` keeps every generated
block and shape class under half of the JVM's method and constant pool limits. The generated classes are the only copy of the
palettes: if they stop compiling after a change of `BlockDefinitions`, see updating.md troubleshooting.

## Behaviour data

```
./gradlew :tools:run --args="behaviour import --cloudburst-data <checkout> --allay <checkout>"
```

writes the capture store `data/behaviour/captures.nbt`, the generated behaviour data and `data/behaviour/REPORT.md` from:

- Paletter's own captures under `data/bds`: Script API dumps (`behaviour-dump`, run with the Beta APIs), and
  experiments on BDS (`behaviour-probe`: door collision, climbing, and the defaults of custom blocks);
- CloudburstMC/Data (Apache-2.0) and AllayMC/Allay (MIT), read from their git history and matched to versions by block
  state hashes. These are third-party and labelled as such.

`update` (and `update --capture-only`, the capture half of a full recapture) runs `behaviour-dump`, `behaviour-probe` and
`education-capture` on the server of its other captures, six more starts of BDS, and stages their files like the other
captures: only when they differ from the committed ones of the build. A step that fails is a FAIL, except the optional
probes (`BehaviourStage.OPTIONAL`, listed in the report header: the behaviour probe, whose measurements come from one
reference build; and the behaviour dump of a preview, as BDS 1.26.70.24 and 1.26.70.26 exit without a word in its world sample,
around `minecraft:straw_bed`, cause unverified), which are a skipped row and a TODO. The recapture's assemble job then runs `behaviour import` on the staged captures and on CloudburstMC/Data and
AllayMC/Allay at the commits pinned in `data/behaviour/sources.json`. That file is the one place of the pins: the workflow
fetches those commits, `behaviour import` fails when a checkout is at another one, and `BehaviourSourcesTest` fails when the
workflow writes a commit of its own. Move a pin together with the regenerated `captures.nbt`, generated classes and
`REPORT.md`.

The report lists the ranking, which source decides each key in each version, disputes, post-processed values and the
changes only a third-party dump shows (below). The same sources at the same commits give the same bytes. Keys that only
have third-party sources are the `NATIVE:` ones in the report; [native-capture.md](native-capture.md) is the plan for
capturing them from BDS.

### Captures and generated code

`data/behaviour/captures.nbt` is the importer's own store (`BehaviourStore` in the tools): every capture with its
coverage and values, disputes, post-processing notes, the defaults of custom content, and the versions `retire` retired.
The library does not read it. `./gradlew :tools:generateBehaviour` (also run by `behaviour import`; checked by
`:tools:checkBehaviour` in `check`) writes `dev.opencollab.paletter.internal.behaviour.vanilla` from it and the bundled
palettes, with JavaPoet (`BehaviourCode`):

- `BehaviourBase`: the oldest version that is not retired. `v.everyBlock()` / `v.everyItem()` set a default per key,
  then one chain per block and item with the keys that differ from it, through typed setters generated from the keys
  (`BlockSetters`, `ItemSetters`): `.destroyTime(1.5f)`; a value of one state property as data,
  `.destroyTime("growth", 0, 0.0f, 7, 0.5f)`; a value of several properties as a shared table constant
  (`BehaviourTables`: `TABLE_<properties>_<hash of the values>`, keyed by property values, never palette order);
  `...Unknown()` where nothing is known. Map colours are written as hex RGBA. Shapes are named constants
  (`BehaviourShapes`: `BOX_0_0_0_16_8_16` for a box with corners on whole pixels, else `SHAPE_` and the first block and key
  that use it, its boxes in the Javadoc). A block's schema (`growth=0..7`) names its states: a state of a palette gets the
  block's values if it has the same properties and each value is one of the schema's (what its state hash would find).
- `BehaviourChanges<version>`: what changed against the version before, each line with a comment naming the capture that
  decided it and the captures of the version that confirm it (or say otherwise), e.g.
  `// destroy_time 0.2 -> 0.3: BDS Script API dump 1.26.45.1, confirmed by CloudburstMC/Data 0021592`. Flags, also listed
  in the report's "Version changes to check": `SOURCE ONLY` (only a third-party dump decided the change; `SOURCE ONLY for
  n of m values` where it decided part of it), `first coverage` (a value where nothing was known before, not a change), and
  `suspected dump artefact` (a change one source makes and takes back in the next version, such as CloudburstMC/Data's
  `requires_correct_tool` in 26.40). New blocks and items say where their values come from. A block or item whose values
  did not change is the same object in both versions at runtime (in 26.60 almost every block changed: it gained the
  climbing and vibration keys).
- `BehaviourSources<version>`: the deciding capture per key and version, and per block or item where it differs (a cell of
  captures for a block whose states different sources cover); `BehaviourMarks`: notes and disputes per capture, each for
  the versions it holds in, and the custom defaults; `BehaviourCaptures`: the captures by source, version and part
  (`SCRIPT_API_26_30_MAP_COLOR`).
- Nothing a source says can end a comment: values in comments and Javadoc escape backslashes, characters outside
  printable ASCII and `*/`.

**BDS first.** The generator resolves each value with the store's lookup (the newest capture covering it decides) and one
rule on top (`BdsFirst`): a value a direct BDS capture gave is never replaced by a third-party dump of a newer version that
says something else. The BDS value stays (inherited), the dump's value is a dispute of it, and the report lists it under
"Needs recapture". Where only dumps have a key, the newest dump of the version is used: the version before is no evidence
for this one, and the change is flagged.
- No lambdas. Methods hold at most 60 statements, classes 8 methods; `GeneratedBehaviourLimitsTest` keeps every method
  under half of the JVM's 64 KB and every constant pool under half of its limit, so growth fails a test, not class loading.

Tests: `GeneratedBehaviourTest` compares every value, capture, note and dispute of every state, item and key of every
bundled palette with the store's lookup and `BdsFirst`; `BehaviourCodeTest` runs the generator on a small store (and
compiles and runs its output). `retire` retires the dropped data version in the store (its captures stay, as what newer
versions inherit, also through later imports once the palette is gone); `generateBehaviour` then makes the next version
the base, with everything it inherited folded in.

The library compiles without the generated package (`VanillaBehaviour` loads `BehaviourData` by name), so the generator
can always run: if the generated classes no longer compile, delete the package and run `generateBehaviour`
(docs/updating.md, troubleshooting).

## Voxel shapes

`voxel-shapes capture --version <build>` (also part of `update`) records the voxel shapes packet of a vanilla world,
of a world with the `voxel_shapes` experiment, of a probe add-on and of anchor blocks, plus BDS's own shape files, into
`data/bds/<build>/voxel-shapes`. `voxel-shapes import` writes `dev.opencollab.paletter.internal.vanilla.shapes` (`ShapeCode`;
`voxel-shapes check`, the Gradle task `checkVoxelShapes` in `check`, fails when it is stale): `VoxelShapeTable` holds every distinct
shape once as the boxes a greedy merge of its cells gives (`ANVIL` for a shape BDS names, `BOX_0_0_0_16_8_16` for one box on whole
pixels, else `SHAPE_` and the first block it is made for; the boxes in pixels in its Javadoc), checked to give the captured grid
again; `VoxelShapes<version>` lists each registry in id order (`s.named("minecraft:anvil", ANVIL)`, `s.block(SHAPE_X, "minecraft:x")`),
`VoxelShapeData` builds them for the bundled data source. The shapes are a table of their own, not the behaviour data's
`BehaviourShapes`: those are `BlockShape`s (boxes as the behaviour probe measured them) of another generator, and sharing would let
one generator's run break the other's classes. `VoxelShapeConformanceTest` checks the library against every capture. The findings
are in [wire-notes.md](wire-notes.md#voxel-shapes).

## BDS schema

`update` runs BDS's documentation generator first (its own start: BDS stops by itself), moves the generated `docs/` into the
cache and writes `data/bds/<build>/schema.json` from `docs/json_schemas/server`. The extract starts at the entry points
(`Item Components`, `Block Components`, `Traits`, and `block/<format>/Components`, the only block one of 1.26.45.1 and 1.26.52.3;
the directory is the format version, `beta` last), follows the `$ref`s and
writes per component and field path (`a.b`, `a[]`, `a{}`) the facts: types, enum, default, minimum and maximum, string and
list limits, pattern, required, deprecated, underlying type and runtime constraint text. A definition that is the same in
several formats is written once with its formats. The file is generated and facts only: the descriptions and the raw tree
stay out of the repository.

`Fixtures#apply` merges the schema into the model, schema before feedback before errata before docs. The schema is part of the add-on, the spec capture, the mapping inference,
the coverage and the component API: one model.

- Per component the newest stable format at or below the add-on's format version counts; `beta` and beta-only components do
  not. Enum values (also of list elements), limits, `step` and `required` replace the docs'; the schema's types are added (first
  where BDS takes none of the documented ones); members and components only the schema has are added (not deprecated ones, not
  the elements of lists and maps). `required` is the union of the schema, the content log and the docs.
- `oneOf`/`anyOf` are read per alternative: `required` only where every object alternative requires it (`requiredInSome`
  otherwise), `minimum`, `maximum` and `default` from one alternative, `enumTypes` for the types an enum came from. Components
  the document around the entry point forbids (`propertyNames`) are deprecated.
- Where the content log and the schema disagree on a limit, list length, step or value, the schema's replaces the log's in
  `Fixtures#facts` and the add-on varies both (`Fixtures#disputed`: boundaries of each, values of each). `update` reports the
  disputes ("BDS schema vs content log"), the components it could not read, the keywords it does not know, and the values the
  add-on generator cut at `MAX_VALUES` ("Add-on values cut", also `valuesCut` in `capture.json`).
- In an `update` run, no docs, a layout the extract cannot read or a schema keyword it does not know is a FAIL: that is how a
  change of the documentation generator shows, and the add-on would otherwise be generated from an older schema in silence.
  Components it could not read are a DIFF, and the previous committed schema (the newest build not after the one being run) is
  what the model merges for them. A committed `schema.json` that cannot be read is no schema, with a warning.
- An `enabled_states` value no docs name a state for, such as `minecraft:sixteen_way_rotation`, adds the state of its own
  name with BDS's values (the Script API's `BlockStates.getAll()` in the newest dump that keeps BDS's value order, format 4 on);
  without one the trait state table skips (and reports) it. Its default is checked against the hash BDS sent, as every other.
  A spec capture made before the table has it leaves the value's states out, reports it ("Trait states") and keeps those
  blocks' creative block ids out of the hash check (`traitStatesUnknown` in `capture.json`).
