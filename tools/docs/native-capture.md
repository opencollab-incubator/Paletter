# Native capture: design (not built yet)

The Script API dump (`behaviour-dump`) and the behaviour probe cover what BDS exposes or what can be measured. Some
behaviour lives only in BDS's own classes and is not exposed anywhere: `BlockType` flags (`mProperties`, 39 flags such as
`Climbable`), material, friction, destroy speed, explosion resistance, flame and burn odds, translucency, thickness,
requires correct tool, and the per-class virtuals of `Item` (attack damage, armour, toughness, enchant value, fuel). Today
these keys come from third-party dumps (CloudburstMC/Data, AllayMC/Allay), ranked below Paletter's own captures. A
native capture would make them Paletter captures of BDS: the `NATIVE:` sources of `BehaviourKeys`.

Both designs below write the same file, `data/bds/<build>/native.json`, so a CI capture and a local one can be diffed:

```
{
  "_generated": "Generated by <tool> ... Do not edit.",
  "bdsVersion": "1.26.63.1",
  "tool": {"name": "endstone" | "levilamina", "version": "..."},
  "blockTypes": {"minecraft:stone": {"mProperties": ["CubeShaped", ...], "mMaterial": {"mType": 1, ...}, "mTranslucency": 0.0,
                 "mThickness": 0.0, "mRequiresCorrectToolForDrops": true, ...}},
  "blockStates": {"<state hash>": {"mDestroySpeed": 1.5, "mExplosionResistance": 6.0, "mFriction": 0.6, "mFlameOdds": 0,
                  "mBurnOdds": 0, "mLightEmission": 0, "mLight": 15, ...}},
  "items": {"minecraft:diamond_sword": {"getAttackDamage": 8, "getArmorValue": 0, "getToughnessValue": 0,
            "getEnchantValue": 10, "mFurnaceXPmultiplier": 0.0, "fuelDuration": 0, ...}}
}
```

Property names are BDS's member and method names (as the LeviLamina headers spell them), so `NATIVE:BlockType.mThickness`
in `BehaviourKeys` names a member of this file and the key check can test it, as it tests `SAPI:` sources against the
behaviour dump. Block states are keyed by the network block state hash, like every other capture.

## Endstone in CI (Linux)

What was checked (2026-11-14):

- Endstone (EndstoneMC/endstone) runs on the Linux `bedrock_server`: its launcher `LD_PRELOAD`s `libendstone_runtime.so`
  into the stripped binary and finds what it hooks by byte signatures (`scripts/configs/linux.toml`). Its own CI builds and
  tests on `ubuntu-22.04`, and its wheels are `manylinux_2_31`, so it can run in GitHub Actions.
- But every Endstone release pins **one** BDS build and downloads exactly that one (SHA-256 checked): v0.11.15 (newest,
  2026-10-28) and `main` pin **1.26.60.6**, not 1.26.63.1. Its C++ plugin API (`include/endstone`) exposes only
  `getMaxStackSize`/`getMaxDurability` of items and nothing behavioural of blocks; the BDS layouts (`src/bedrock`, e.g.
  `BlockType::properties_` at +304) are internal headers, valid only for the pinned build.
- The Endstone team's own data dumps do follow every build: EndstoneMC/bedrock-data branch `r26_u6` is a dump of
  **1.26.63.1** with `block_types.json` (thickness, translucency, requires correct tool, material type, ...) and
  `items.json` (attack damage, armour, toughness, enchant value, fuel, ...). It is made by `bedrock-dumper` (not public),
  whose public predecessor `protocol-dumper` is an `LD_PRELOAD` library built and run on `ubuntu-latest` in GitHub
  Actions against any BDS build (`-DBEDROCK_SERVER_VERSION=latest`), reading the server's own reflection (cereal, EnTT)
  instead of offsets. bedrock-data has no licence, so Paletter cannot bundle it; it is a third-party cross-check at most.

Verdict: **Endstone itself does not run on BDS 1.26.63.x** (only its pinned 1.26.60.6), so an Endstone plugin cannot
capture the builds Paletter captures. The `LD_PRELOAD` approach Endstone's dumpers use does run in GitHub Actions on any
Linux build. No proof of concept was built: this machine has no Linux to run `bedrock_server` on (no WSL distribution, no
Docker), and the members that matter (`BlockType` fields) are not in BDS's reflection, so a dumper needs per-build
signatures, which is the upkeep Endstone pays.

If it is built, the CI design is:

1. A job on `ubuntu-latest` downloads the Linux BDS of the build (`BdsDistribution`, as `bds-inventory` does).
2. It builds a small `LD_PRELOAD` library (clang, libc++ like BDS) that hooks the end of server startup, walks
   `BlockTypeRegistry` and `ItemRegistryManager`, writes `native.json` as above, and exits BDS.
3. Members are found by signature per build (the Endstone `linux.toml` approach); a signature that does not match fails the
   job, so a build never gets a silently wrong field.
4. `behaviour import` reads `native.json` as the `NATIVE` source, ranked with the Script API above the third-party dumps.

## LeviLamina on Windows (local, by hand)

The trusted local cross-check. LeviLamina (LiteLDev/LeviLamina) is a Windows BDS mod loader whose headers are generated
from Mojang's symbols: member names and layouts are BDS's own, which is where the `NATIVE:` names come from. v26.60.7
(2026-11-12) is current; its tooth depends on `github.com/LiteLDev/bds` 1.26.60 and on `bedrock-runtime-data`
(26.60.6-server.14), which is how it follows patch builds. LiteLDev/bds has tags up to v1.26.63; whether lip installs
1.26.63 under LeviLamina 26.60.7 is to be checked when installing.

Install (Windows, in an empty directory):

```
lip install github.com/LiteLDev/LeviLamina        # installs BDS and LeviLamina
lip install <the dump mod's tooth or a local path>
bedrock_server_mod.exe
```

The mod (C++, the LeviLamina mod template):

- On `ServerStartedEvent`, for every `BlockType` in `BlockTypeRegistry`: `mProperties` as flag names (`BlockProperty`),
  `mMaterial`, `mTranslucency`, `mThickness`, `mRequiresCorrectToolForDrops`, `mCanSlide`, `mFalling`; for every `Block`
  (permutation) of it: `mDirectData` (`mDestroySpeed`, `mExplosionResistance`, `mFriction`, `mFlameOdds`, `mBurnOdds`,
  `mLightEmission`, `mLight`) and the state hash.
- For every `Item` in the item registry: `getAttackDamage()`, `getArmorValue()`, `getToughnessValue()`,
  `getEnchantValue()`, `mFurnaceXPmultiplier`, and the furnace fuel duration of a stack of it.
- Writes `native.json` (the format above, `tool.name` `levilamina`) and stops the server.

Run it by hand on the same build as a CI capture, copy `native.json` next to the build's other captures, and diff the two
files (`data-diff`-style, member by member); a difference is a bug in one of the dumpers, not something to pick a side on.
