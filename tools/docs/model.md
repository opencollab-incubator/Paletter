# Component model

Paletter's custom item and block API mirrors Bedrock's add-on component model and compiles it to each protocol's wire
format. The machine-readable model it is generated from is built from the official creator docs and Bedrock Dedicated
Server only.

```
docs  --DocsParser--> data/model/components.json   every component and field, as documented
                      + fixtures.json (hand: errata, samples, companions)
                      + bds-feedback.json (generated: what BDS said last time)
                      + bds-keys.json (generated by the key probe: keys BDS accepts that the docs omit)
      --AddonGenerator--> spec add-on (~1900 items/blocks, one per varied field value) + variants.json
BDS   --spec-capture--> data/bds/<version>/spec/
      --MappingInference--> data/model/mappings.json (JSON -> wire rule per field, per protocol window),
                            coverage.md, bds-feedback.json   (+ transforms.json, hand: what no rule explains)
```

```
./gradlew :tools:generateModel [-Pdocs=/path/to/minecraft-creator]   # docs -> components.json (default: pinned commit)
./gradlew :tools:generateAddon                                        # -> tools/build/spec-addon
./gradlew :tools:run --args="spec-capture --channel release"          # BDS run -> data/bds/<version>/spec
./gradlew :tools:inferMappings                                        # -> mappings.json, coverage.md, bds-feedback.json
./gradlew :tools:checkMappings                                        # part of check: committed outputs up to date
```

`spec-capture` takes the `update` options `--version`, `--cache`, `--keep-server`, `--port`, `--timeout`,
`--experiments`. A second capture after the first inference gives valid bases for components whose docs omit a required
field (run until `bds-feedback.json` stops changing).

## What BDS says that the docs do not

BDS wins over the docs, and what it says is read back from its own output, never typed in:

- **Types.** The content log's type errors become errata when the model is read (`Fixtures.apply`): "expected an object"
  at a field the docs type as a string (`geometry.n_way_visual_rotation`) adds the object type and puts it first (the
  add-on keeps the docs type, so every capture asks again; the API offers only the object);
  "expected a key/value object" at an element of a list (`embedded_visual.material_instances[0]`) of a field that also
  has an object type says the list is the form BDS does not take. "must define at least one ..." (`nonEmpty`) keeps a
  member whose members the model does not know out of the bases. All of it is in `bds-feedback.json`, rewritten by `infer`.
- **Keys** (`spec-capture --probe-keys`, see below): `data/model/bds-keys.json`.
- **Format versions** (`spec-capture --format-sweep`, see below): `data/bds/<version>/spec-format/format-sweep.json`.

### The key probe

`spec-capture --probe-keys [--vanilla-pack <dir>]` asks BDS about keys the docs do not list: a candidate is one variant per
trivial value (a boolean, an integer, a string that names nothing, the first enum value of the object the key sits in, `{}`,
`[]`) of the component's base. The candidates are only chosen from three sources, never used as values:

1. **The BDS binary.** Its error and description texts name keys next to each other ("'alpha_masked_tint' requires a
   non-default 'tint_method'"). A text that names a field the model knows by a specific name (an underscore, six or more
   characters) makes its other quoted or underscored identifiers candidates at the level of that field; a text that names
   `minecraft:x` makes them candidates of the component's root. (The binary does not order strings by component, so
   neighbours in the file say nothing.) The same texts name format versions ("... member with 'format_version' < 1.21.70",
   "only supported at format_version 1.21.120 or higher"): those are the `minFormatVersion` of an accepted key.
2. **wiki.bedrock.dev.** The markdown of its component pages (keys as bullets of a backticked key, a dash and a type,
   nested) and format histories (what each version added, "Versioned" labelled or not) is fetched from the bedrock-wiki
   repository into `<cache>/wiki`, and read as untrusted text: identifier tokens and version numbers only.
3. **Vanilla packs.** The `blocks` and `items` JSON of the server's behavior packs and of `--vanilla-pack` (the BDS zip
   ships none today; a bedrock-samples checkout has them).

BDS answers per key: blocks log "not present in the Schema" for a key it does not know (`unknown`), a type error for a known
key of the wrong type (`known`, with the error), nothing for a key and type it takes (`accepted`, with the types). Items log
nothing for members they ignore, so an item key is `accepted` only when it changes the wire against the base (else `inert`).
`bds-keys.json` holds the answers of the newest probed build; `Fixtures.apply` adds each accepted key as a field (doc text
`(bds-schema <build>) ...`, the format version from BDS's texts), so the next normal `spec-capture` varies it. A key that
needs another key beside it (`alpha_masked_tint` needs a `tint_method` and `render_method: opaque`) goes in `fixtures.json`
`together`, with BDS's own text as the reason. Keys a build already answered are not asked again.

### The format sweep

A normal capture writes one `format_version`, so a wire value that depends on it looks constant. `spec-capture
--format-sweep` writes `spec-format/`: per component, the base at every format boundary (BDS's texts, the wiki's
"Versioned" changes, the docs' `minFormatVersion`), at the known version just below it and at the reference (the capture's
format); per key with a boundary the same with the key set. Fields that need a newer format than the file are left out of the
base. `format-sweep.json` lists for each what BDS refused and which wire leaves differ from the reference, with the bits that
differ. It is evidence for a hand transform, not an input of `infer` (the capture is not under `spec/`).

## The docs model

Source: github.com/MicrosoftDocs/minecraft-creator, `creator/Reference/Content/` (CC BY 4.0, see
`data/model/ATTRIBUTION.md`). The component pages share one layout, which `DocsParser` reads. Descriptions,
`menu_category`, states, permutations and traits come from hand-written pages and are modelled as pseudo components
(`item:description`, `block:states`, `block:permutations`, `block:trait:minecraft:...`). Per component: id, kind,
category, docs status, description, minimum format version, experiments, value forms. Per field (flattened path
`a.b`, `a[]`, `a{}`): JSON types, default, required, enum values, range, minimum format version, examples.

## The variants

Per component: a **control** (only the companions it needs; for companions that need each other, `geometry` and
`material_instances`, the minimal accepted pair), a **base** (every field without a documented default, or
that BDS reported as required, set to a sample), every whole value form, and per field one variant per value (omitted,
booleans, numbers around the ranges and the default, every enum value, lists of 0/1/2 elements, empty and filled maps
and objects). Each variant is its own item (`paletter:<component>_<n>`) or block (`paletter:b_<component>_<n>`).

## The inference

A variant is accepted when BDS sent it and logged no error. The control shows what a component adds to the wire
(`sent`, `server-only`, `rejected`); per field the variants are compared with the base, and every changed wire leaf is
explained by the first rule that fits all observations:

| kind | meaning |
|---|---|
| `identity` | the leaf is the JSON value (possibly renamed, moved into `item_properties`, another NBT type) |
| `linear` | scale * value + offset (unit conversions) |
| `table` | a value table, for booleans and enums |
| `affix` | free strings with a constant prefix/suffix |
| `bitset` | a list of enum values -> an int of bits |
| `element` | list element k -> the leaf |
| `constant`, `empty-list` | a leaf the field's presence switches on |

`whenAbsent` gives the leaf when the field is omitted. A field no leaf follows is `dropped` (server only); one whose
every variant is rejected is `rejected`. Leaves no rule explains make a field `partial`/`unresolved`; those need a named
transform in `transforms.json`.

One capture per bundled protocol (`data/bds/<version>/spec`). Its add-on asks for the format version of its build, and
the capture keeps its own `variants.json`. A capture whose wire relevant part equals the previous window's joins it
(`protocols`); a different one is kept beside it as `protocol<N>`. `bds-feedback.json` is read from the newest capture
only.
